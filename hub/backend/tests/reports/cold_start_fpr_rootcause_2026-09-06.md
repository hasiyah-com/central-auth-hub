# วินิจฉัยสาเหตุ FPR ที่ holdout สูงกว่า validation (cold start)

วันที่ 6 ก.ย. 2569 · สืบเนื่องจาก Round 2b / 2c ที่ไม่ผ่าน per-size gate
สถานะ: **วินิจฉัยโครงสร้างข้อมูล — ไม่ใช่การเลือก threshold และไม่มีการเปลี่ยน production**

## 0. คำถาม

Round 2b/2c พบ challenge FPR @ size 50 บน holdout = 1.23% / 1.18% ขณะที่
validation-tuning ให้ค่าเฉลี่ย 0.583% (sd 0.107%, max-of-5 = 0.733%)
ห่างกัน ~5–6 sd จึงเกินกว่าจะอธิบายด้วยความบังเอิญของการสุ่ม seed

สมมติฐานที่ตั้งไว้และผลการทดสอบ:

| # | สมมติฐาน | ผล |
|---|---|---|
| H1 | population variance ของ seed (แก้ด้วยการเพิ่ม seed) | **หักล้าง** |
| H2 | split/time effect — holdout อยู่ไกลจาก calibration | **หักล้าง** |
| H3 | ความแปรปรวนระดับ **ผู้ใช้** (cluster) | **ยืนยัน** |

## 1. เครื่องมือ

- `ml-service/scripts/diag_split_distance.py` — challenge FPR ต่อ block ย่อยของ test
- `ml-service/scripts/diag_user_concentration.py` — แยก FPR ราย user ต่อ block
- `ml-service/scripts/diag_u01_burst.py` — องค์ประกอบของการตัดสิน (policy floor vs ชั้นใด)

Config B · gamma 1.0 · thresholds `{warn 0.98, challenge 0.995, block 0.9999}`
ใช้ seed 42–46 ซึ่ง holdout **ถูกเปิดไปแล้ว** ใน Round 1 — ใช้เพื่อวินิจฉัยโครงสร้าง
ข้อมูลเท่านั้น ไม่ได้ใช้เลือกค่าใด ๆ (บันทึกไว้ตามกฎ B68)

## 2. H2 ถูกหักล้าง — ระยะห่างจาก calibration ไม่ใช่ตัวขับ

แบ่ง test (episode 120–139) เป็นบล็อกย่อย · challenge FPR @ size 50:

| seed | tune (ep110-119) | testA (ep120-129) | testB (ep130-139) | test_all |
|---|---|---|---|---|
| 42 | 0.517% | 0.483% | 0.267% | 0.375% |
| 43 | 0.467% | 0.433% | 0.517% | 0.475% |
| 44 | 0.550% | **1.467%** | 0.850% | 1.158% |
| 45 | 0.650% | 1.017% | 0.767% | 0.892% |
| 46 | 0.733% | **2.183%** | 1.000% | 1.592% |
| **mean** | 0.583% | 1.117% | 0.680% | 0.898% |

ถ้าระยะห่างจาก calibration เป็นตัวขับ ต้องได้ `tune < testA < testB`
ที่พบคือ **testA > testB ใน 4/5 seed** ทั้งที่ testA อยู่ใกล้กว่า → หักล้าง

## 3. H1 ถูกหักล้างด้วยเหตุผลเชิงโครงสร้าง

`build_profiles_v2.SPEC` เป็นรายการโปรไฟล์ **12 คนที่ตายตัว** (U01–U12)
การเปลี่ยน seed เปลี่ยนเฉพาะการสุ่มของ RNG **ไม่ได้เพิ่มผู้ใช้ใหม่**

→ การเพิ่ม validation seeds เพิ่มเพียงจำนวน realization ของโปรไฟล์ 12 ตัวเดิม
ไม่ได้เพิ่มความหลากหลายของหน่วยที่เป็นต้นเหตุความแปรปรวน **จึงแก้ปัญหาไม่ได้**

## 4. H3 ยืนยัน — FPR กระจุกที่ผู้ใช้คนเดียว

challenge FPR ราย user @ size 50:

| user | seed46 tune | seed46 testA | seed44 tune | seed44 testA | seed42 testA |
|---|---|---|---|---|---|
| **U01** | 4.00% | **16.20%** | 0.60% | **11.20%** | 0.00% |
| U06 | 0.80% | 3.20% | 0.80% | 0.60% | 1.40% |
| U09 | 0.40% | 2.60% | 0.40% | 0.80% | 0.20% |
| อื่น ๆ | ≤1.20% | ≤1.40% | ≤2.60% | ≤3.20% | ≤1.40% |

- seed 46 testA: U01 คนเดียวกิน **61.8%** ของ FPR ทั้งหมด (top-3 = 84.0%)
- seed 44 testA: U01 กิน **63.6%** (top-3 = 87.5%)
- seed 42 (ที่ holdout **ต่ำกว่า** validation): ไม่มีใครระเบิด สูงสุด 1.40% → กระจาย 24.1%

→ ค่า FPR ระดับ seed ถูกกำหนดโดย "U01 ระเบิดหรือไม่ในบล็อกนั้น" เป็นหลัก

## 5. กลไก — L2 Behavior ไม่ใช่ policy floor

แยกองค์ประกอบของ 81 เหตุการณ์ที่ U01 ถูก challenge (seed 46 · testA · size 50):

```
policy min_action distribution: {None: 81}     ← policy floor = 0 เหตุการณ์
policy floor reasons:           {}
ชั้นที่ให้หลักฐานสูงสุด:        {behavior: 79, rule: 2}
```

**97.5% มาจากชั้น L2 Behavior Profiling** ไม่ใช่ policy floor และไม่ใช่ rule

### cold start ขยายผล แต่ไม่ใช่ต้นเหตุทั้งหมด

U01 · seed 46 · testA: **16.20% @ size 50 → 4.40% @ size 5000** (ลด 3.7 เท่า)
แต่ U01 ยังเป็นผู้สนับสนุนอันดับ 1 ที่ size 5000 (44.0% ของ FPR รวม)

→ U01 เป็นโปรไฟล์ที่ **แปรปรวนสูงโดยธรรมชาติ** (hour_peaks 2 ค่า `[8, 15]`,
สองอุปกรณ์ 0.72/0.28) · โปรไฟล์พฤติกรรมที่สร้างจาก 50 เหตุการณ์ครอบคลุมโหมดรอง
ไม่พอ → เหตุการณ์ปกติที่มาจากโหมดรองถูกตีเป็นเบี่ยงเบน

## 6. เหตุผลที่การยก threshold ไม่ได้ผลใน Round 2b/2c

ECDF ถูก fit แบบ **รวมทุกผู้ใช้** (`fit_all` รวม `beh_s` จากทุกคน) ผู้ใช้ที่
สเกลคะแนนพฤติกรรมสูงกว่าคนอื่นอย่างเป็นระบบจึงตกอยู่ในเปอร์เซ็นไทล์บนของ
การกระจายรวมตลอดเวลา · การยก challenge 0.9898 → 0.995 ตัดหางล่างของผู้ใช้
ส่วนใหญ่ออก แต่ผู้ใช้ที่อิ่มตัวอยู่แล้วยังอยู่เหนือเกณฑ์ → FPR ไม่ลดตามที่หวัง

นี่คือคำอธิบายที่ตรงหลักฐานของ "threshold tuning ไม่ช่วย" — ต่างจากที่รายงาน
Round 2c เคยอ้างว่าเป็น `login_velocity` (ข้อสรุปนั้นถูกแก้แล้วใน B69)

## 7. ผลต่อความถูกต้องของการวัด

**แก้จากฉบับแรกของรายงานนี้:** เกณฑ์ตัดสิน (`macro["challenge_fpr"]`) ไม่ได้เป็น
pooled event-level อย่างที่เขียนไว้ตอนแรก — `tune.macro()` เฉลี่ยระดับผู้ใช้ก่อน
แล้วจึงเฉลี่ยข้าม cell · ในชุดนี้ทุกผู้ใช้มีจำนวนเหตุการณ์เท่ากัน (1,000 ต่อคน)
ค่า macro จึงเท่ากับ pooled พอดี (ตรวจแล้วใน `round2c_archive/final_result.json`:
`macro = pooled = 0.01182` ที่ size 50)

ข้อบกพร่องที่แท้จริงจึงไม่ใช่การถ่วงน้ำหนัก แต่คือ **gate เทียบค่าประมาณจุดกับงบ
โดยไม่มีการวัดความไม่แน่นอนเลย** ทั้งที่หน่วยอิสระมีเพียง 12 และหนึ่งในนั้น
ครองสัดส่วนกว่าครึ่ง → ค่า 1.18% มีช่วงความเชื่อมั่นกว้างมาก การประกาศ
"ผ่าน/ไม่ผ่าน" จากค่าจุดจึงตัดสินเกินกว่าที่ข้อมูลรองรับ

`bootstrap.hierarchical_proportion()` คำนวณ CI แบบ cluster-aware ได้อยู่แล้ว
แต่ `_final_gate()` ไม่ได้เรียกใช้

## 8. ข้อสรุป

1. ช่องว่าง validation→holdout **ไม่ใช่** population variance ของ seed และ
   **ไม่ใช่** ผลของระยะห่าง split
2. เป็นความแปรปรวนระดับผู้ใช้ที่ขยายด้วย cold start · หน่วยตัวอย่างที่แท้จริง
   มีเพียง 12 และคงที่ทุก seed
3. กลไกคือ L2 Behavior (ดูรายละเอียดใน §10)
4. **การเพิ่ม validation seeds แก้ปัญหานี้ไม่ได้** — แผนเดิมถูกหักล้าง

## 9. บันทึกความซื่อตรง

- ใช้ holdout seed 42–46 ที่ spent แล้ว เพื่อวินิจฉัยโครงสร้าง ไม่ใช่เลือกค่า
- ไม่มีการแก้ threshold, config, หรือโค้ด production ในรอบนี้
- Round 2c ยังคงสถานะ `failed_gate` · production ยังเป็น fallback เดิม · L3 shadow

## 10. กลไกระดับสัญญาณ — โหมดที่ชอบธรรมแต่หายไปจากตัวอย่างเล็ก

แยกเหตุผลของ L2 ใน 81 เหตุการณ์ที่ U01 ถูก challenge (seed 46 · testA · size 50):

```
reason tags ใน normal ทั้งหมด:
  hour_rarity 106 · hours_diff 81 · new_subsystem 78 · scope_escalation 78 · weekend_mismatch 34
reason tags ใน normal ที่ถูก challenge:
  new_subsystem 78 · scope_escalation 78 · hour_rarity 20 · hours_diff 14 · weekend_mismatch 7
```

**78 จาก 81 เหตุการณ์มี `new_subsystem` และ `scope_escalation` ยิงพร้อมกัน**

### ต้นตอ: SUB_A หายไปจากชุดฝึก 50 เหตุการณ์

โปรไฟล์ของ U01 (`build_profiles_v2.SPEC`) คือ `subsystems {HUB: 0.9, SUB_A: 0.1}`

| size | subsystem ในชุดฝึก | `seen_subsystems` |
|---|---|---|
| 50 | `{HUB: 50}` | `{HUB}` ← **ไม่มี SUB_A เลย** |
| 500 | `{HUB: 450, SUB_A: 50}` | `{HUB, SUB_A}` |
| 5000 | `{HUB: 4574, SUB_A: 426}` | `{HUB, SUB_A}` |

holdout ของ U01 มี `{HUB: 894, SUB_A: 106}` → **ทุกครั้งที่ล็อกอินเข้า SUB_A
(10.6% ของเหตุการณ์) ถูกตีเป็น "ระบบที่ไม่เคยใช้"** → `NEW_SUBSYSTEM_SCORE` +0.30
และ `scope_escalation` +0.25 ยิงตามเพราะ SUB_A มี scope สูงกว่า HUB

### ปัญหาที่สอง: คะแนน L2 เป็นแลตทิซ และมวลก้อนหนึ่งอยู่เหนือเกณฑ์แค่ 0.0005

การกระจายคะแนน behavior ของ U01 (500 เหตุการณ์ปกติ) มีเพียง 13 ค่าที่ต่างกัน:

| score | สัดส่วน | ECDF | ผ่านเกณฑ์ challenge 0.995? |
|---|---|---|---|
| 0.00 | 53.0% | 0.0000 | |
| 0.30 | 14.2% | 0.8840 | |
| 0.40 | 1.6% | 0.9693 | |
| 0.50 | 2.6% | 0.9747 | |
| **0.55** | **9.8%** | **0.9955** | **ใช่ (เกินมา 0.0005)** |
| ≥0.60 | 4.8% | ≥0.9973 | ใช่ |

`0.55 = 0.30 (new_subsystem) + 0.25 (scope_escalation)` — มวล 49 เหตุการณ์ที่ค่าเดียว
วางอยู่เหนือเกณฑ์แค่ 0.0005 · การขยับ threshold จึงไม่ใช่การแลกเปลี่ยนแบบราบเรียบ
แต่เป็นการ **กระโดดทีละก้อน** ตามแลตทิซ

นี่คือคำอธิบายสุดท้ายว่าทำไม Round 2b (0.9898) และ 2c (0.995) ให้ผลใกล้เคียงกัน:
ทั้งสองค่าอยู่ **ใต้** 0.9955 เท่ากัน มวลก้อนเดียวกันจึงข้ามเกณฑ์ทั้งคู่

## 11. ผลต่อทางเลือกที่เสนอไว้

- **per-user ECDF (ทางเลือก 3 เดิม) แก้เคสนี้ไม่ได้** — ที่ size 50 ผู้ใช้มีเพียง
  50 เหตุการณ์ การประมาณควอนไทล์ที่ 0.995 ต้องการอย่างน้อยหลักร้อย และคะแนนเป็น
  แลตทิซหยาบ (53% อยู่ที่ 0.0) · ยิ่งกว่านั้น ปัญหาไม่ได้อยู่ที่สเกลของคะแนน
  แต่อยู่ที่ **สัญญาณยิงผิด**: SUB_A เป็นพฤติกรรมชอบธรรมของ U01 ที่กลุ่มตัวอย่างเล็ก
  มองไม่เห็น
- สิ่งที่ตรงเหตุคือ **ถ่วงน้ำหนักความมั่นใจของสัญญาณ novelty ตามขนาดประวัติ** —
  "ไม่เคยเห็น" จากประวัติ 50 เหตุการณ์เป็นหลักฐานที่อ่อนกว่า "ไม่เคยเห็น" จาก 5,000
  (rule of three: n=50 ไม่มีการพบเลย → ขอบบนของความถี่จริง ~6% ซึ่ง**ไม่ตัดทิ้ง**
  โหมด 10%) · เป็นแนวเดียวกับ `MIN_HISTORY_FOR_RARITY` และ Laplace smoothing
  ที่โมดูลนี้ใช้อยู่แล้วกับ `hour_rarity`
