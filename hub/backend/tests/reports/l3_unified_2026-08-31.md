## 1. 🔴 ข้อค้นพบหลัก — ระบบที่วัด ≠ ระบบที่รัน

### 1.1 สิ่งที่พบ

การทดลองทุกชุดที่ใช้สรุปผลเรียก `aggregate()` โดยตั้ง IForest เป็นศูนย์:

```python
# exp_final_gate.py:204 · exp_lc_v3.py:157 · exp_campaign_level.py:93
access = aggregate(rule, beh, NEUTRAL).decision   # NEUTRAL = IForestResult(0.0, 0.0)
```

แต่ production เรียกด้วยคะแนนจริง:

```python
# risk_engine.py:97 (ก่อนแก้)
iforest_result = map_score(ml_result["anomaly_score"])   # +0.10 / +0.20 / +0.40
decision = aggregate(rule_result, behavior_result, iforest_result, shadow_mode)
# risk_aggregator.py:68  total = rule.score + behavior.score + iforest.risk_score
```

`map_score` บวกได้สูงสุด **+0.40** เทียบกับ threshold `challenge = 0.70` และ `block = 0.85`
คือ **57% ของเกณฑ์ challenge** — มากพอพลิกผลการตัดสินได้ด้วยตัวเอง

**แปลว่าตัวเลข recall/FPR ที่ freeze ไว้ อธิบายระบบที่ไม่เคยถูก deploy**

### 1.2 ผลกระทบจริง (login_sessions 1,024 รายการที่มี breakdown ครบ)

| การตัดสิน (L1+L2 เท่านั้น) | → | การตัดสินจริงใน production | n | % |
|---|---|---|---|---|
| allow | → | allow | 453 | 44.2% |
| block | → | block | 286 | 27.9% |
| warn | → | warn | 152 | 14.8% |
| challenge | → | challenge | 5 | 0.5% |
| **allow** | → | **warn** | **65** | **6.3%** |
| **warn** | → | **challenge** | **41** | **4.0%** |
| **challenge** | → | **block** | **22** | **2.1%** |

- **128 / 1,024 = 12.5%** ของการตัดสินถูกกำหนดโดย IForest ไม่ใช่ L1/L2
- **22 ครั้งถูก block** โดยชั้นที่การทดลองวัดว่าไม่มีส่วนร่วม
- IForest มีค่า > 0 ใน **44.6%** ของ session (เฉลี่ย +0.141 เมื่อ > 0)
- **ทุกการเปลี่ยนเป็นการยกระดับความเข้ม** ไม่มีเคสไหนผ่อนลง (เพราะ `map_score` บวกอย่างเดียว)

                + (risk_breakdown::jsonb->>'behavior')::numeric AS l12

           WHERE jsonb_exists(risk_breakdown::jsonb,'iforest'))
SELECT ... -- ดูคำสั่งเต็มใน §8

### 1.3 สิ่งที่แก้

`aggregate()` รับ IForest ที่ `risk_score = 0.0` เสมอ — **คงค่าดิบไว้ครบ** ตัดเฉพาะอิทธิพล:

```python
# risk_engine.py (หลังแก้)
decision = aggregate(rule_result, behavior_result, monitoring_only(), shadow_mode)
```

`breakdown["iforest_raw"]` ยังเก็บคะแนนจริง · `iforest_explanation` (SHAP 23 ฟีเจอร์) ยังส่งให้ UI
เหมือนเดิม — เปลี่ยนแค่ว่ามันไม่ถูกบวกเข้าคะแนนความเสี่ยงอีก

**นี่ไม่ใช่การลดความสามารถของระบบ แต่คือการทำให้ production ตรงกับสิ่งที่วัดมาแล้ว**
สัญญาณไม่ได้หายไป — ย้ายไปออกที่แกน monitoring แทน (§4)

### 1.4 ผลพลอยได้ด้านความทนทาน

access decision **ไม่ขึ้นกับ ml-service อีกต่อไป** — แข็งแรงกว่า fail-safe เดิมที่ "ml ล่ม →
แทนคะแนนด้วย 0.0" ซึ่งก็คือการเปลี่ยนผลการตัดสินตามสถานะของบริการภายนอกอยู่ดี
ตอนนี้ ml-service ล่ม = สิทธิ์ผู้ใช้ไม่กระทบเลย แม้แต่นิดเดียว

## 2. SHAP ของ sequence-residual (18 มิติ)

`TreeExplainer` ผูกกับโมเดล IForest **รายคน** เก็บใน `_MODEL_CACHE` เดียวกัน จึงสร้าง
ครั้งเดียวต่อการ fit ไม่ใช่ต่อ request (ถ้าสร้างทุกครั้งจะเป็นคอขวดแบบเดียวกับ B63)

ชื่อฟีเจอร์ = `{dim}_{stat}_w5` จาก 6 residual dims × [mean, slope, ptp]:

```
gap_log_mean_w5   scope_mean_w5   passkey_age_log_mean_w5   ... (mean × 6)
gap_log_slope_w5  scope_slope_w5  ...                       (slope × 6)
gap_log_ptp_w5    scope_ptp_w5    ...                       (ptp × 6)
```

ลำดับต้องตรงกับ `_windows()` เป๊ะ (`[mean×6, slope×6, ptp×6]`) — map ผิดลำดับ = SHAP
ชี้ฟีเจอร์ผิดตัวโดยไม่มีใครรู้ **บทเรียนเดียวกับ B49** มีเทสคุมชื่อทั้ง 18 ตัว

**ผลจริง** (ผู้ใช้ประวัติ 1,500 แถว · residual สุดโต่ง 9.0 ทุกมิติ):

```
monitoring : l3_investigate
detected_by: ['sequence_residual'] | unique: True
seq        : tier=extreme raw=0.7391 elig=warn
--- top_factors ---
  passkey_age_log_ptp_w5  l3_sequence  contrib=0.2207  shap=+0.67370  anomaly
  weekday_usage_slope_w5  l3_sequence  contrib=0.2165  shap=+0.66080  anomaly
  weekday_usage_ptp_w5    l3_sequence  contrib=0.1910  shap=+0.58300  anomaly
  sub_rarity_ptp_w5       l3_sequence  contrib=0.1900  shap=+0.58000  anomaly
  gap_log_ptp_w5          l3_sequence  contrib=0.1817  shap=+0.55460  anomaly
```

เครื่องหมายกลับด้านให้ **บวก = ดันไปทาง anomaly** เหมือน `model.py` (SHAP อธิบาย
`decision_function` ซึ่งค่าสูง = ปกติ ส่วนคะแนนที่ใช้จริงคือ `-score_samples`)

### 2.1 ⚠️ ข้อจำกัดที่พบระหว่างทดสอบ — SHAP ของ sequence **อิ่มตัว**เมื่อหลุด distribution ทุกมิติ

> 🔴 **ถอนข้อสรุปของหัวข้อนี้ (1 ก.ย. 2569)** — เนื้อหาด้านล่างคงไว้ตามเดิมเพื่อให้เห็น
> ว่าเคยสรุปอย่างไร แต่**ใช้อ้างอิงไม่ได้แล้ว** การวัดละเอียดขึ้นพบว่า:
>
> 1. SHAP **ไม่ได้**พังเพราะคะแนนอิ่มตัว — มันพัง**ก่อน**คะแนนอิ่มตัว โดยเริ่มเสื่อม
>    ตั้งแต่จุดที่ระบบเริ่มขึ้นธง (ที่ base=5 คะแนนยังแยกได้ครบ 6 ค่า แต่ SHAP ถูก 2/6)
> 2. ทางแก้ที่เสนอไว้ ("อ่าน SHAP เฉพาะย่านที่คะแนนยังแยกแยะได้") **ใช้ไม่ได้**
>    เพราะย่านที่ยิงแล้วและ SHAP ยังถูก แทบไม่มีอยู่จริง
> 3. สาเหตุที่สรุปผิด: ทดลองเพียง 2 จุดปลายทาง ซึ่งบังเอิญอยู่คนละฝั่งของทั้งเกณฑ์ยิง
>    และเพดานพอดี จึงเห็นเป็นความสัมพันธ์เชิงสาเหตุที่ไม่มีจริง
>
> **คำอธิบายหลักเปลี่ยนเป็น robust deviation รายมิติแล้ว** (ชี้ถูก 6/6 ทุกย่าน)
> และ `top_factors` เปลี่ยนชื่อเป็น `diagnostic_factors`
> → ดู [`l3_explainability_2026-09-01.md`](l3_explainability_2026-09-01.md)


ตอนเขียน parity test เจอพฤติกรรมที่ต้องบันทึกไว้ (วัดในคอนเทนเนอร์ ml-service โดยตรง
บน history N(0,1) 1,500 แถว · threshold p99.9 = 0.5580):

| ลักษณะ window | คะแนน | ยิง? | SHAP ชี้มิติถูก |
|---|---|---|---|
| มิติเดียวสุดโต่ง (`cur[j]=25`, ที่เหลือ 0) | 0.484–0.512 | ❌ | ✅ **6/6** |
| ทุกมิติสุดโต่ง (`8.0`) + มิติ j เด่นสุด (`30.0`) | **0.7439 เท่ากันทุก j** | ✅ | ❌ **1/6** |

แถวล่าง: คะแนนออกมา**เท่ากันเป๊ะทั้ง 6 กรณี** และ SHAP ตอบ `gap_log_slope_w5` ทุกครั้ง
ไม่ว่ามิติไหนจะเด่นกว่า — เพราะจุดที่หลุด distribution ไปทุกมิติแล้วถูก IsolationForest
isolate ที่ความลึกเท่ากันหมด (อิ่มตัว) SHAP จึงเหลือแค่สะท้อนว่าต้นไม้บังเอิญ split
ฟีเจอร์ไหนก่อน ไม่ได้สะท้อนว่ามิติไหนผิดปกติมากกว่ากัน

**ผลต่อการใช้งาน:** เวลา sequence view ยิงจริง (ซึ่งคือกรณีหลุด distribution) ชื่อฟีเจอร์
ใน `top_factors` **บอกไม่ได้ว่ามิติไหนคือสาเหตุ** — ใช้ยืนยันได้แค่ว่า "พฤติกรรมช่วงนี้
ผิดปกติในเชิงร่วม" ซึ่งตรงกับธรรมชาติของ joint-residual detector แต่ไม่ตรงกับสิ่งที่
ผู้อ่านคาดหวังจากคำว่า "คำอธิบาย"

**[ถอนแล้ว — แก้เมื่อ 1 ก.ย. 2569 ด้วย robust deviation]** ข้อความเดิม: บันทึกเป็นข้อจำกัดที่ทราบ แนวทางที่เป็นไปได้ถ้าจะแก้: ใช้ background
dataset ของผู้ใช้คนนั้น (`feature_perturbation="interventional"`) แทน tree_path_dependent
หรือรายงาน z-score รายมิติควบคู่ SHAP · ทั้งสองทางต้องวัด latency ใหม่

**ส่วนที่ยืนยันได้แน่นอนคือ index mapping** — แถวบน 6/6 พิสูจน์ว่า `SEQ_FEATURE_NAMES`
เรียงตรงกับ `_windows()` จริง (ความเสี่ยงแบบ B49 ปิดแล้ว) เทสจึงอ่านจาก
`sequence.explanation` ในย่านที่ยังแยกแยะได้ ไม่ใช่ย่านอิ่มตัว

**ผลพลอยได้:** `sequence.explanation` ตอนนี้คืนค่าแม้ **ไม่ยิง** — ใช้ไล่ปัญหา/ตรวจสอบได้
ต่างจาก `top_factors` ที่รวมเฉพาะ view ที่ยิงจริงตามการออกแบบ

**mask `keep`** — forest fit เฉพาะคอลัมน์ที่ std > 1e-9 จึงต้อง map index กลับเป็นตำแหน่ง
เดิมก่อนตั้งชื่อ ไม่งั้นชื่อจะเลื่อนทุกครั้งที่มีมิติใดนิ่งจนถูกตัดออก

## 3. duplicate ratio + unique_to_l3 (ใน runtime ไม่ใช่สคริปต์ทดลอง)

| ตัวชี้วัด | ขอบเขต | นิยาม |
|---|---|---|
| `unique_to_l3` | ต่อเหตุการณ์ | L3 ขึ้นธง **และ** `access_decision == allow` |
| `duplicate_ratio` | สะสม | สัดส่วนครั้งที่ L3 ยิงแล้ว L1/L2 จับได้อยู่แล้ว |
| `duplicate_window` | สะสม | ตัวหาร = จำนวนครั้งที่ L3 ยิงทั้งหมด |

**ทำไมต้องคืน `duplicate_window` มาด้วยเสมอ:** ratio ต้องมีตัวหาร ถ้าเห็นแค่ `1.00`
จะอ่านไม่ออกว่ามาจาก 1 เหตุการณ์หรือ 1,000 เหตุการณ์ — เป็นค่า**สะสม** ไม่ใช่ rolling window
(ตัวนับอยู่ที่ Redis `l3dup:flagged` / `l3dup:dup`, `INCR` ผ่าน pipeline)

**นับเฉพาะเหตุการณ์ที่ยิงจริง** — ถ้านับ login ปกติเข้าไปด้วย ratio จะถูกเจือจางจนไร้ความหมาย
(มีเทสคุมข้อนี้: `test_quiet_event_does_not_move_duplicate_counter`)

ผลตรวจ: ยิง 4 ครั้ง (challenge, block, allow, allow) → `duplicate_ratio = 0.5`, `window = 4` ✅

## 4. รวมเป็นผล L3 เดียว สองมุมมอง

```
POST /v1/l3-evaluate  {user_id, features[23], residual[6]|null, access_decision}

  L3 point view     IForest 23 ฟีเจอร์   -> "login ครั้งนี้ผิดปกติไหม"   + SHAP
  L3 sequence view  IForest 18 มิติ      -> "พฤติกรรมช่วงนี้ผิดปกติไหม" + SHAP
                          ↓ รวม
  {monitoring_decision, is_anomaly, unique_to_l3, detected_by,
   duplicate_ratio, duplicate_window, top_factors[{feature, owner, contribution}]}
```

- hub เรียก **ครั้งเดียว** แทนสองครั้ง (`/v1/score` + `/v1/sequence-score` ยังอยู่เพื่อ backward compat)
- `residual = null` → ข้าม sequence view เหลือ point view (กรณีปิดแฟล็ก) ไม่ใช่ error
- `access_decision` ส่งเข้าไปเพื่อ **วัด** `unique_to_l3` เท่านั้น — ผลที่คืนมาไม่มีฟิลด์
  access decision เลย

**`contribution` เทียบข้ามมุมมองตรงๆ ไม่ได้** — SHAP ของสองโมเดลอยู่คนละสเกล จึง
normalize ภายในมุมมองตัวเอง (`|shap| / Σ|shap|` ของมุมมองนั้น) ให้อ่านได้ว่า "ฟีเจอร์นี้
อธิบายสัญญาณของมุมมองตัวเองกี่เปอร์เซ็นต์" และคง `shap` ดิบไว้ด้วยเพื่อไม่ให้ข้อมูลหาย
ทุก factor ติดป้าย `owner` (`l3_point` / `l3_sequence`) เสมอ

**เกณฑ์ขึ้นธงของ point view ใช้ 0.70 ไม่ใช่ 0.50** — โมเดล 23 ฟีเจอร์เทรนบนข้อมูลจำลอง
และวัด optimism bias ไว้แล้ว ใช้เกณฑ์ต่ำจะท่วม SOC ด้วยสัญญาณที่ยังพิสูจน์ไม่ได้บน traffic จริง
(เป็นค่าของช่องเฝ้าระวังล้วน ปรับได้โดยไม่กระทบสิทธิ์ผู้ใช้)

## 5. 🔒 การคุ้มครองสองแกน — ตอนนี้ครอบคลุม L3 ทั้งหมด

```text
access_decision     = L1/L2/L4 -> allow | warn | challenge | block
monitoring_decision = L3        -> normal | l3_investigate
```

| กฎที่บังคับด้วยเทส | ผล |
|---|---|
| `apply_channel()` (API เดิมที่ผสมสองแกน) ต้องไม่มีอีก | ✅ |
| คำศัพท์สองแกน disjoint (รวม `would_*`) | ✅ |
| `monitoring_decision(result)` ไม่รับ access decision เข้ามา | ✅ ตรวจจาก signature |
| sequence view เปิด/ปิด → `decision`/`score`/`reasons` เท่าเดิมเป๊ะ | ✅ |
| **point view ทุกระดับคะแนน (0.0/0.35/0.55/0.75/0.99) → access ไม่ขยับ** | ✅ **ใหม่** |
| **ตัดอิทธิพลแล้วสัญญาณต้องไม่หาย — ต้องโผล่ที่แกน monitoring** | ✅ **ใหม่** |
| ml-service ตอบคำในแกน access กลับมา → client ปัดเป็น `normal` | ✅ **ใหม่** |
| `breakdown["iforest"]` = 0.0 แต่ `iforest_raw` = ค่าจริง | ✅ |

จุดสุดท้ายสำคัญ: ถ้าใครแก้ ml-service ให้ตอบ `"challenge"` มา แล้ว hub เชื่อตรงๆ ก็เท่ากับ
เปิดทางให้ L3 สั่ง access decision ได้อีกโดยไม่ต้องแก้ hub เลย — `_coerce_unified()` ปิดช่องนี้

## 6. "L3 พัง" ≠ "L3 abstain"

ทั้งสองกรณีคืน `fired=False` เหมือนกัน ถ้าบันทึกเป็น contract ทั้งคู่ การ replay จะนับ L3
ที่ล่มว่าเป็น "ตัดสินใจไม่ยิงอย่างถูกต้อง" ซึ่งเป็นตัวเลขที่หลอกตัวเอง (**บทเรียน B61**)

→ `_sequence_contract()` คืน `None` เมื่อปิดแฟล็ก **หรือ** มี error · breakdown ใส่คีย์
`l3_sequence` เฉพาะตอนมีค่าจริง

## 7. Fail-safe (B21) ที่ตรวจแล้ว

| สถานการณ์ | ผล |
|---|---|
| ml-service ล่ม | `l3_unreachable: *` · monitoring=normal · **access ไม่กระทบ** |
| ml-service ช้าเกิน `l3_timeout_seconds` | `l3_timeout` · เงียบ |
| residual ผิดมิติ | sequence abstain · **point view ยังทำงาน** (ไม่ล่มทั้งชั้น) |
| Redis ไม่พร้อม | sequence abstain · duplicate counter คืน `(None, 0)` |
| SHAP import พัง | `explanation = []` · คะแนนยังใช้ได้ (SHAP เป็นคำอธิบาย ไม่ใช่ตัวตัดสิน) |
| L3 ระเบิดทั้งชั้น | decision ปกติ · `l3_sequence = None` |

WITH s AS (
  SELECT (risk_breakdown::jsonb->>'iforest')::numeric AS ifo,
         (risk_breakdown::jsonb->>'rule')::numeric
       + (risk_breakdown::jsonb->>'behavior')::numeric AS l12
  FROM login_sessions

    AND jsonb_exists(risk_breakdown::jsonb,'rule')
    AND jsonb_exists(risk_breakdown::jsonb,'behavior')

              WHEN least(l12+ifo,1.0)>=0.7 THEN 'challenge'
              WHEN least(l12+ifo,1.0)>=0.5 THEN 'warn' ELSE 'allow' END AS with_ifo
  FROM s)
SELECT without_ifo, with_ifo, count(*) FROM d GROUP BY 1,2 ORDER BY 3 DESC;"

## 10. ยังไม่ได้ทำ / ข้อจำกัด

- **`duplicate_ratio` เป็นค่าสะสมทั่วระบบ** ไม่ใช่ rolling window และไม่แยกตามผู้ใช้/subsystem
  — พอสำหรับตอบ "L3 คุ้มไหม" ในภาพรวม แต่ยังตอบรายกลุ่มไม่ได้
- ✅ **parity ของลำดับ 18 มิติ ปิดแล้ว** — `test_shap_names_point_at_the_right_dimension`
  ทดสอบครบทั้ง 6 มิติ (6/6 ถูก) ความเสี่ยงแบบ B49 ในส่วนนี้ปิดแล้ว
- ⚠️ **SHAP ของ sequence อิ่มตัวเมื่อยิงจริง** — ดู §2.1 · เป็นข้อจำกัดที่ทราบ ยังไม่ได้แก้
  และเป็นข้อที่ควรบอกผู้เชี่ยวชาญตรงๆ ก่อนเขาถาม
- **ข้อจำกัดเชิงโครงสร้างเดิมยังอยู่** — ที่อัตราใช้งานจริง 1.65 ครั้ง/วัน/คน ผู้ใช้ต้องใช้เวลา
  ~1.7 ปีถึงจะถึง tier `warn` ที่ sequence view ขึ้นธงได้ (ดู `l3_shadow_replay`)
  การเพิ่ม SHAP/duplicate ratio ไม่ได้แก้ข้อนี้
- **`POINT_INVESTIGATE = 0.70` ยังไม่ได้ calibrate กับ traffic จริง** — ตั้งจากเหตุผลเชิงหลักการ
  (optimism bias) ควรวัด SOC load จริงก่อนล็อกค่า
