# (1) ปรับ threshold L3 ให้ FPR ≤1% · (2) พยายามอุดจุดอ่อน L1/L2 ต่อ campaign

**วันที่:** 26 ส.ค. 2026 · seeds 42–46 (mean ± CI95) · ชุด holdout (final attack ที่ไม่เคยใช้พัฒนา)

## (1) ✅ สำเร็จ — L3 FPR 2.3% → 0.8%

### threshold sweep (บน final holdout)

| quantile | L3 FPR | L3 unique | ผ่านเกณฑ์ ≤1% |
|---|---|---|---|
| p99 | 2.14% | 5.31% | ❌ |
| p99.3 | 1.76% | 4.39% | ❌ |
| p99.5 | 1.52% | 3.66% | ❌ |
| p99.7 | 1.19% | 3.35% | ❌ |
| **p99.9** | **0.79%** | **2.43%** | ✅ |

**เลือก p99.9** — จุดเดียวที่เข้างบ FPR

**ต้นทุนที่ต้องยอมรับ:** unique ลดจาก 5.1% → **2.3%** (ครึ่งหนึ่ง)
เป็นการแลกที่ตรงไปตรงมา: คุม false positive ให้ SOC ทำงานไหว โดยยอมจับได้น้อยลง

**ทำไม p99 บน validation ให้ FPR จริง 2.1%:** validation กับ test เป็นคนละ episode
distribution จึงต่างกันเล็กน้อย → quantile ที่ calibrate ไว้ต่ำเกินจริง

## (2) ⚠️ ไม่สำเร็จตามหวัง — ได้แค่ +0.6pp

### วินิจฉัย: L1/L2 พลาด campaign family ไหน (final holdout)

| family | อัตราพลาด | สัญญาณที่ได้ |
|---|---|---|
| `u_subsystem_shuffle` | **58%** | `weekend_mismatch (+0.10)` เท่านั้น |
| `u_scope_only` | **52%** | `weekend_mismatch (+0.10)` เท่านั้น |
| `u_off_f_axis` | 45% | `weekend_mismatch (+0.10)` เท่านั้น |
| `u_intermittent` | 43% | `weekend_mismatch (+0.10)` เท่านั้น |
| `u_mixed_direction` | 29% | บางส่วนไม่มีสัญญาณเลย |

สัญญาณเดียวที่ได้คือ **+0.10** ซึ่งห่างจาก warn (0.5) มาก

### สิ่งที่ทำ: เพิ่ม `scope_escalation` เข้า L2 (Tier 3)

L2 เดิมมี hour rarity · subsystem novelty/rarity · cadence · device signature
แต่ **ไม่มีอะไรวัด "ระดับสิทธิ์ที่เข้าถึง เทียบกับปกติของคนนั้น"** → เป็นช่องว่างจริง

```
scope_escalation: current_scope − p90(scope ของคนนี้) ≥ 0.2  →  +0.25 (soft, ไม่มี floor)
```

TDD 6/6 ผ่าน · production ใช้สูตร scope เดียวกับ `feature_extraction._SCOPE_WEIGHTS`

### ผลจริง: campaign recall 20.7% → **21.3%** (+0.6pp เท่านั้น)

**เหตุผล — ตรวจจากข้อมูลจริง:**

| ผู้ใช้ | p90 ของ scope | scope ที่ใช้จริง |
|---|---|---|
| U01 | 0.80 | {0.0, 0.8} |
| U03/U04/U06 | 0.60 | {0.0, 0.6} |
| U05 | 0.80 | {0.0, 0.8} |

ผู้ใช้เหล่านี้ **ใช้ subsystem ที่ scope สูงอยู่แล้วเป็นประจำ** (10–40% ของ login)
→ p90 = เพดานของเขาเอง → campaign ที่ "ยกระดับ scope" ไปยัง subsystem ที่เขาใช้อยู่แล้ว
**ไม่ถือเป็นการยกระดับ** สำหรับคนนั้น → สัญญาณไม่ยิง (ถูกต้องแล้ว ไม่ใช่บั๊ก)

ส่วนผู้ใช้ที่ p90 = 0.0 (เช่น U02 ใช้ HUB อย่างเดียว) การเข้า subsystem ใหม่จะทริป
**subsystem novelty (challenge floor)** อยู่แล้ว → scope escalation ซ้ำซ้อน

## ข้อสรุปที่สำคัญกว่าตัวเลข

> **campaign family เหล่านี้ "แยกไม่ออกในระดับเหตุการณ์เดี่ยว" โดยธรรมชาติ**
> ทุก login ใช้เครื่องที่เคยใช้ · subsystem ที่เคยใช้ · ชั่วโมงปกติ · จังหวะปกติ
> สิ่งที่ผิดปกติคือ **รูปแบบของลำดับ** (สลับไปมา / ทิศตรงข้าม / สลับ phase) เท่านั้น

**⇒ ไม่มีสัญญาณระดับ per-event ใดใน L2 ที่จะจับได้ — นี่คือโดเมนของ L3 โดยโครงสร้าง**

การพยายามอุดที่ L1/L2 ต่อไปจะเป็นการ **ปรับให้ตรง family เหล่านี้ = overfitting รอบใหม่**
ซึ่งขัดกับเหตุผลที่สร้าง holdout ตั้งแต่แรก

### สถานะของ scope_escalation

**เก็บไว้** — เป็นสัญญาณที่ถูกหลักการ ไม่มีต้นทุน (Challenge FPR 1.6% ไม่ขยับ)
และครอบคลุมเคสจริงที่ชุดทดสอบนี้ไม่มี: ผู้ใช้ที่มี scope profile แคบ แล้วขยับไป subsystem
ที่ **เคยใช้แต่นานๆ ที** (subsystem novelty ไม่ยิงเพราะเคยใช้)

**แต่ต้องรายงานตรงๆ ว่าไม่ได้ช่วยบน holdout ชุดนี้** — ไม่นับเป็นความสำเร็จของ (2)
