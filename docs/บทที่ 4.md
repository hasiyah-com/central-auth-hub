## 4.1 บทนำ

บทนี้นำเสนอผลการพัฒนา **Central Auth Hub** ซึ่งเป็นระบบศูนย์กลางการยืนยันตัวตนและจัดการสิทธิ์ผู้ใช้ (Centralized Identity & Permission Management Platform) สำหรับมหาวิทยาลัย โดยระบบไม่ได้ออกแบบให้เป็น Single Sign-On (SSO) ในความหมายที่ผู้ใช้ล็อกอินครั้งเดียวแล้วเข้าทุกระบบย่อยได้ทันที แต่ Hub ทำหน้าที่เป็น **ผู้ออกบัตรยืนยันตัวตนและตัดสินสิทธิ์** ให้กับแต่ละระบบย่อยผ่าน OAuth 2.0 + PKCE ส่วน session ของแต่ละระบบย่อยยังคงแยกจากกันโดยสมบูรณ์

ในการพัฒนาจริง โครงการนี้ประกอบด้วย 4 ส่วนหลักที่ทำงานร่วมกัน ได้แก่ Hub (Central Auth Server, FastAPI + PostgreSQL + Redis), Hub Admin Frontend (Next.js 14), ระบบย่อยตัวอย่าง 2 ระบบคือระบบหอพักและระบบห้องสมุด (แต่ละระบบเป็น OAuth client ที่มีฐานข้อมูลและ session ของตัวเอง) และ ML Verifier ซึ่งเป็นบริการแยกที่ทำหน้าที่ประเมินความเสี่ยงของการล็อกอินด้วย Isolation Forest

บทนี้แบ่งการนำเสนอผลออกเป็น 4 ส่วน ส่วนแรกคือผลการพัฒนาฟีเจอร์ของระบบ (4.2) ได้แก่ Authentication Hub, การจัดการผู้ใช้และระบบย่อย, Passkey/WebAuthn และ Account Recovery ส่วนที่สองคือผลการพัฒนา Hybrid Risk-Based Authentication (RBA) แบบ 4 ชั้น (4.3) ส่วนที่สามคือผลการทดลองโมเดล Machine Learning ที่ใช้ในชั้นที่ 3 ของ RBA ได้แก่ชุดข้อมูล การประเมินประสิทธิภาพ และการอธิบายผลด้วย SHAP (4.4-4.6) และส่วนสุดท้ายคือผลการทดสอบระบบทั้งหมด ทั้ง Unit Test, Integration Test, Security Test และการทดสอบ Risk-Triggered MFA แบบ end-to-end (4.7-4.8) ปิดท้ายด้วยการอภิปรายผลและสรุป (4.9-4.10)

ตัวเลขและผลลัพธ์ทั้งหมดที่นำเสนอในบทนี้มาจากการรันจริงบนโค้ดของระบบ ไม่ใช่ตัวเลขสมมติ — ผลการประเมินโมเดลในหัวข้อ 4.5 และค่า SHAP ในหัวข้อ 4.6 ได้จากการรันสคริปต์ฝึกโมเดล (`train_model.py`) และ SHAP TreeExplainer กับชุดข้อมูลจริงใน `ml-service/data/sessions.csv` และโมเดลที่บันทึกไว้จริงที่ `ml-service/models/iforest_v1.pkl` ส่วนผลการทดสอบในหัวข้อ 4.7 มาจากผลรัน pytest ของชุด test ทั้งหมดใน `hub/backend/tests/`

## 4.2 ผลการพัฒนาระบบ

### 4.2.1 Authentication Hub และ Admin Console

หัวใจของระบบคือ Hub (พอร์ต 8000) ซึ่งพัฒนาด้วย FastAPI + SQLAlchemy ทำหน้าที่ 3 อย่างหลัก คือเป็น OIDC Identity Provider ที่รับ identity จาก Google OAuth แล้วแปลงเป็น JWT ของ Hub เอง เป็นนายหน้า OAuth 2.0 + PKCE ให้ระบบย่อยขอ token และเป็นผู้ตัดสินความเสี่ยงของแต่ละ session ผ่าน RBA 4 ชั้นก่อนปล่อยให้ผู้ใช้เข้าระบบ

แผนภาพด้านล่างแสดงสถาปัตยกรรมการ deploy ของระบบทั้งหมด แบ่งเป็น 3 Docker Compose stack เชื่อมต่อกันผ่าน external network `cah-net`

รูปที่ 4.1 แสดงหน้า Dashboard ของ Hub Admin Console ซึ่งประกอบด้วยการ์ดสรุปจำนวนผู้ใช้/ระบบย่อย/เซสชันความเสี่ยง และกราฟ time-series ของ anomaly score ในรอบ 24 ชั่วโมงล่าสุด

### 4.2.2 ระบบจัดการผู้ใช้งาน (User Management)

หน้า `/admin/users` ของ Hub Admin Frontend เรียกข้อมูลจาก endpoint `GET /admin/users` ของ Hub ซึ่งอยู่ภายใต้ dependency `require_hub_admin` แอดมินสามารถค้นหาและกรองผู้ใช้ตาม `user_type` (student/teacher/staff/admin) และ `faculty` ได้ เนื่องจากผู้ใช้ทั้งหมดในระบบมาจากการ seed ข้อมูลจริง 100 รายชื่อ (70 นักศึกษา + 15 อาจารย์ + 10 เจ้าหน้าที่ + 5 แอดมิน) ตามที่ออกแบบไว้ใน `seed_users.py` หน้านี้จึงทำหน้าที่เป็น read-only directory ของผู้ใช้ในมหาวิทยาลัยมากกว่าเป็นหน้า CRUD แบบทั่วไป โดยข้อมูลสิทธิ์การเข้าถึงระบบย่อยของแต่ละคนถูกจัดการแยกผ่านตาราง `access_list` ในหน้า Subsystems/Whitelist ไม่ใช่ในหน้านี้

นอกจากหน้า User Management แล้ว Hub Admin Frontend ยังมีหน้า **Pending Triage** สำหรับตรวจสอบ session ที่ RBA ให้คะแนนความเสี่ยงอยู่ในช่วงที่ควรเฝ้าระวัง หน้า **Audit Log Viewer** สำหรับไล่ดู `audit_logs` ทั้งหมดแบบ append-only หน้า **ML Threshold Preview** ที่ให้แอดมินทดลองปรับค่า threshold ของ Risk Aggregator แล้วดูผลกระทบต่อ distribution ของ decision พร้อมแถบ SHAP อธิบายแต่ละฟีเจอร์ หน้า **IP Blacklist** และหน้า **API Alerts** สำหรับติดตามรูปแบบการยิง request ที่ผิดปกติ

รูปที่ 4.2 แสดงหน้า User Management ที่รายชื่อผู้ใช้ทั้งหมดพร้อมตัวกรองตามประเภทผู้ใช้และคณะ

### 4.2.3 ระบบจัดการ OAuth Client (Developer Portal)

ระบบย่อยแต่ละตัว (เช่น ระบบหอพักและระบบห้องสมุด) ต้องลงทะเบียนเป็น OAuth client กับ Hub ก่อนจึงจะขอ token ได้ ฟังก์ชันนี้อยู่ใน Developer Portal (`/developer/*`) ซึ่งเปิดให้ผู้ใช้ที่เป็น teacher/staff/admin เท่านั้น (ผ่าน `require_developer`)

ขั้นตอนการลงทะเบียนคือ ผู้พัฒนาเรียก `POST /developer/subsystems` พร้อมชื่อระบบ, `redirect_uris` และ `scope` ที่ต้องการ ระบบจะสร้าง `client_id`, สุ่ม `client_secret` แล้วเก็บเฉพาะค่า hash (Argon2id) ไว้ในตาราง `subsystems` ส่วน secret ตัวจริงจะถูกเข้ารหัสด้วย Fernet และเก็บไว้ใน `secret_retrieval_tokens` ชั่วคราว แล้วส่งลิงก์ one-time กลับไปให้ผู้พัฒนาเปิดดูได้ครั้งเดียวผ่าน `GET /secret/retrieve?token=...` ภายใน 15 นาที — เมื่อเปิดหน้าแล้ว ตัว HTML จะใช้ `history.replaceState()` ลบ token ออกจาก URL ทันที เพื่อไม่ให้ token หลุดไปอยู่ใน browser history หรือ log

หลังลงทะเบียน ระบบย่อยจะมีสถานะ `pending` จนกว่าแอดมินจะอนุมัติผ่าน `POST /admin/subsystems/{id}/approve` จากนั้นผู้พัฒนาสามารถอัปโหลด whitelist รายชื่อผู้ใช้ที่อนุญาตให้เข้าระบบย่อยนั้นได้ ทั้งแบบอัปโหลดเป็นไฟล์ CSV (`POST /developer/subsystems/{id}/whitelist`) และแบบเพิ่มทีละคน (`POST .../whitelist/user`) การถอนสิทธิ์ใช้วิธี soft delete โดยตั้งค่า `revoked_at` ในตาราง `access_list` เพื่อรักษาประวัติไว้

รูปที่ 4.3 แสดงหน้าจัดการ OAuth Client ใน Developer Portal ซึ่งแสดงรายการระบบย่อยที่ลงทะเบียน สถานะ (pending/active/suspended) และปุ่มจัดการ whitelist

### 4.2.4 ระบบ Passkey Authentication (WebAuthn)

ระบบรองรับการล็อกอินแบบไม่ใช้รหัสผ่านด้วย Passkey ตามมาตรฐาน WebAuthn/FIDO2 ซึ่งพัฒนาครบทั้ง 8 phase ได้แก่ การลงทะเบียน (registration ceremony) การล็อกอิน (authentication ceremony) การจัดการอุปกรณ์ (เปลี่ยนชื่อ/ลบ credential) การกู้คืนบัญชีด้วย backup code การยืนยันตัวตนซ้ำแบบ step-up (re-authentication) มาตรการป้องกัน enumeration (B43) และการตรวจจับ signature counter ที่ผิดปกติ (counter-regression) ซึ่งเป็นสัญญาณของการคัดลอก credential

**Passkey Registration** — ผู้ใช้ที่ล็อกอินด้วย Google แล้วสามารถเพิ่ม Passkey จากอุปกรณ์ที่รองรับ เช่น Windows Hello, Touch ID หรือ Face ID ได้จากหน้าตั้งค่าบัญชี ทุก credential ที่ลงทะเบียนจะถูกเก็บไว้ในตาราง `passkey_credentials` พร้อม public key, sign count เริ่มต้น และ timestamp สำหรับใช้คำนวณ `passkey_age_days` ในฟีเจอร์ ML ภายหลัง เมื่อลงทะเบียน Passkey ตัวแรกสำเร็จ ระบบจะออก backup code จำนวน 10 ชุดให้ผู้ใช้เก็บไว้ โดย backup code แต่ละชุดถูก hash ด้วย Argon2id ก่อนบันทึก

**Passkey Login** — ผู้ใช้สามารถเข้าสู่ระบบโดยไม่ต้องผ่าน OAuth ของ Google เลย เบราว์เซอร์จะขอให้ผู้ใช้ยืนยันตัวตนผ่านไบโอเมตริกหรือ PIN ของอุปกรณ์ Hub จะตรวจสอบ signature ที่ได้กับ public key ที่เก็บไว้ และตรวจสอบว่า `sign count` ใหม่มากกว่าค่าเดิมเสมอ (กันการ clone authenticator) Passkey ที่ลงทะเบียนแล้วยังถูกนำมาใช้เป็นส่วนหนึ่งของ Risk-Triggered MFA ด้วย — เมื่อ RBA ตรวจพบความเสี่ยงระดับปานกลาง ผู้ใช้ที่มี Passkey จะถูกขอให้ยืนยันตัวตนซ้ำผ่าน Passkey ทันที (รายละเอียดในหัวข้อ 4.8)

รูปที่ 4.4 แสดงหน้าลงทะเบียน Passkey ซึ่งแสดงสถานะอุปกรณ์ที่ลงทะเบียนแล้วและปุ่มเพิ่มอุปกรณ์ใหม่

[ภาพ Passkey Registration]

รูปที่ 4.5 แสดงหน้าล็อกอินด้วย Passkey ซึ่งเรียก browser WebAuthn API ให้ผู้ใช้ยืนยันตัวตนผ่านไบโอเมตริกหรือ PIN ของอุปกรณ์

### 4.2.5 ระบบ Account Recovery

เนื่องจาก Passkey ผูกกับอุปกรณ์ ระบบจึงต้องมีทางกู้คืนบัญชีในกรณีที่ผู้ใช้ทำอุปกรณ์หาย ทางออกหลักที่ออกแบบไว้คือ **Backup Code** จำนวน 10 ชุดที่ออกให้ตอนลงทะเบียน Passkey ครั้งแรก ผู้ใช้สามารถใช้ backup code แทน Passkey เพื่อเข้าระบบและลงทะเบียนอุปกรณ์ใหม่ได้ แต่ละโค้ดใช้ได้ครั้งเดียว (ถูก mark ว่าใช้แล้วทันทีที่ verify ผ่าน)

อีกเส้นทางหนึ่งคือ **Account Recovery flow** ซึ่งถูกออกแบบมาเฉพาะสำหรับกรณีที่เบราว์เซอร์หรืออุปกรณ์ของผู้ใช้ไม่รองรับ WebAuthn เลย — ในกรณีนี้ระบบจะ**ไม่**ปล่อยให้ผู้ใช้ fallback ไปใช้การยืนยันด้วย Email OTP เพื่อล็อกอินตรง ๆ (ซึ่งจะลดระดับความปลอดภัยจาก phishing-resistant กลับไปเป็นแบบเดิม) แต่จะนำผู้ใช้ไปยังหน้า Account Recovery ที่ต้องใช้ backup code หรือให้แอดมินช่วยตรวจสอบตัวตนแทน (กฎ B46)

ส่วน **Email OTP** ในระบบนี้ถูกออกแบบให้ใช้เป็น "ประตู" ก่อนการลงทะเบียน Passkey บังคับ (Force Enrollment) สำหรับผู้ใช้ที่มีความเสี่ยงระดับปานกลางแต่ยังไม่มี Passkey และพ้นช่วง grace period แล้ว — กล่าวคือ OTP ในที่นี้ใช้เพื่อพิสูจน์ว่าผู้ใช้ยังเข้าถึงอีเมลของตัวเองได้ ก่อนจะอนุญาตให้สร้าง Passkey ใหม่ (B45) ไม่ใช่ใช้แทนการล็อกอินหลัก

รูปที่ 4.6 แสดงหน้า Account Recovery ที่ให้ผู้ใช้กรอก backup code เพื่อยืนยันตัวตนแทน Passkey ที่สูญหาย

## 4.3 ผลการพัฒนาระบบ Risk-Based Authentication

ระบบใช้แนวคิด **Hybrid Risk-Based Authentication (RBA)** แบบ 4 ชั้น ซึ่งรวมเอา Rule Engine, Behavior Profiling, Machine Learning (Isolation Forest) และ Risk Aggregator เข้าด้วยกัน — แต่ละชั้นให้คะแนนความเสี่ยงเป็นตัวเลขที่บวกสะสมกันได้ ไม่ใช่การ "vote" หรือ "เลือกโมเดลที่ดีที่สุด" แบบที่อาจเข้าใจผิดได้ ทั้งหมดทำงานภายใน `feature_extraction.py` และ `risk_aggregator` ของ Hub โดยรันทุกครั้งที่มีการล็อกอินผ่าน OAuth flow

แผนภาพด้านล่างแสดงสถาปัตยกรรมของ RBA 4 ชั้นตั้งแต่จุดรับ login ไปจนถึงการตัดสินใจ

```text
Login Event (OAuth callback / Passkey verify)
        │
        ▼
feature_extraction.py  ──  สกัด feature 23 ตัวจาก session + DB history
        │
        ├─── [Layer 1]  rule_engine.py  (Deterministic)
        │    ├── Hard-block rules  →  score = 1.0 (บล็อกทันที)
        │    └── Cumulative rules  →  risk_score_rule  (0.0–1.0)
        │
        ├─── [Layer 2]  behavior_profiling.py  (Personalized)
        │    ├── query login_sessions 30 วันย้อนหลัง
        │    └── เปรียบเทียบกับ baseline ของผู้ใช้คนนั้น
        │         →  risk_score_behavior  (0.0–0.9)
        │
        ├─── [Layer 3]  ml_client.py  →  ml-service:9000  (Isolation Forest)
        │    ├── POST /v1/score  (feature vector 23 ค่า)
        │    ├── รับ anomaly_score + SHAP values
        │    └── แปลงเป็น  risk_score_ml  (0.0–0.4)
        │         [fail-safe: ถ้า ML ล่ม → risk_score_ml = 0.0]
        │
        └─── [Layer 4]  risk_aggregator.py
             total = min(risk_score_rule + risk_score_behavior + risk_score_ml, 1.0)
             │
             ├── total ≥ 0.85  ──►  block
             ├── total ≥ 0.70  ──►  challenge  (Risk-Triggered MFA)
             ├── total ≥ 0.50  ──►  warn  (allow + log เพื่อเฝ้าระวัง)
             └── total <  0.50  ──►  allow
```

### 4.3.1 Layer 1 — Rule Engine

ชั้นแรกใช้กฎที่กำหนดไว้ล่วงหน้า (deterministic rules) แบ่งเป็น 2 กลุ่ม

กลุ่ม **Hard-block rules** — ถ้าเข้าเงื่อนไขใดเงื่อนไขหนึ่งจะถูกตัดสินว่าเสี่ยงสูงทันที โดยไม่ต้องรอผลจาก ML เลย ได้แก่ `failed_logins_24h` ≥ 10 ครั้ง, `login_count_24h` ≥ 50 ครั้ง, `country_change_count_30d` ≥ 8 ครั้งในเดือนเดียว, IP อยู่ใน blacklist หรือ pattern ที่บ่งบอกถึง impossible travel (ล็อกอินจากสองประเทศห่างไกลภายในเวลาไม่ถึง 1 ชั่วโมง)

กลุ่ม **Cumulative score rules** — ให้คะแนนสะสม เช่น อุปกรณ์ใหม่ (+0.30), ประเทศใหม่ (+0.30), User-Agent family ใหม่ (+0.20), failed login ≥ 3 ครั้งในช่วงสั้น (+0.20), ล็อกอินจากนอกประเทศไทย (+0.10), และมีมากกว่า 5 บัญชีล็อกอินจาก IP เดียวกันภายใน 1 ชั่วโมง (+0.25)

ผลลัพธ์ที่ได้คือ ชั้นนี้สามารถดักจับเหตุการณ์ที่มีความเสี่ยงชัดเจนได้ทันทีโดยไม่ต้องพึ่งโมเดล ML เลย เช่น การโจมตีแบบ brute-force หรือ credential stuffing ที่มี failed login จำนวนมากในเวลาสั้น ๆ

---

### 4.3.2 Layer 2 — Behavior Profiling

ชั้นที่สองเปรียบเทียบ session ปัจจุบันกับพฤติกรรมปกติของผู้ใช้คนนั้นในช่วง 30 วันที่ผ่านมา เช่น ช่วงเวลาที่มักล็อกอิน (`hours_from_typical_login_time`), ประเทศที่ใช้งานประจำ, อุปกรณ์ที่ใช้งานประจำ และวันในสัปดาห์ที่มักใช้งาน

เกณฑ์ที่ใช้ ได้แก่ ส่วนต่างของเวลาล็อกอินจากเวลาปกติ ≥ 10 ชั่วโมง (+0.40) หรือ ≥ 6 ชั่วโมง (+0.20), ล็อกอินจากประเทศใหม่ (+0.30), ใช้อุปกรณ์ใหม่ (+0.20), และล็อกอินวันเสาร์-อาทิตย์ทั้งที่ปกติใช้งานเฉพาะวันธรรมดา (+0.10)

เนื่องจากการเปรียบเทียบกับ baseline ต้องมีประวัติการล็อกอินมาก่อน ระบบจึงกำหนด **cold start policy** — ผู้ใช้ที่มีประวัติ login session น้อยกว่า `MIN_HISTORY_FOR_PERSONALIZATION = 5` ครั้ง จะได้ค่าคงที่ 0.20 แทน เพื่อไม่ให้ผู้ใช้ใหม่ถูกตัดสินว่า "ผิดปกติ" ทุกครั้งเพียงเพราะยังไม่มีข้อมูลพอจะสร้าง baseline

ผลลัพธ์คือชั้นนี้สามารถตรวจจับพฤติกรรมที่ผิดไปจากความเคยชินของผู้ใช้แต่ละคนได้ แม้ IP หรืออุปกรณ์นั้นจะไม่อยู่ใน blacklist ของชั้นที่ 1 เลยก็ตาม

### 4.3.3 Layer 3 — Machine Learning (Isolation Forest)

ชั้นที่สามเป็นบริการแยกชื่อ **ML Verifier** (พอร์ต 9000) ใช้โมเดล **Isolation Forest** (Liu, Ting & Zhou, 2008) เพียงโมเดลเดียว ไม่ได้เปรียบเทียบกับ One-Class SVM หรือ Local Outlier Factor ตามที่เคยร่างไว้ในแผนเดิม — เหตุผลคือ Isolation Forest เหมาะกับงาน anomaly detection แบบ unsupervised ที่ข้อมูลผิดปกติมีน้อยมากเมื่อเทียบกับข้อมูลปกติ (กรณีของการล็อกอิน) มีค่า time complexity ใกล้เคียง O(n log n) ทำให้ inference เร็วพอสำหรับ real-time scoring และไม่ต้อง assume การกระจายตัวของข้อมูลแบบโมเดลที่อิง distance เช่น LOF

Hub เรียก `POST /v1/score` ของ ML Verifier พร้อมเวกเตอร์ฟีเจอร์ 23 ค่า (ตารางที่ 4.1) ได้ผลลัพธ์เป็น `anomaly_score` ซึ่งถูกแปลงต่อเป็นคะแนนความเสี่ยงของชั้นนี้ตามช่วง: anomaly_score ≥ 0.7 → +0.40, ≥ 0.5 → +0.20, ≥ 0.3 → +0.10, น้อยกว่านั้น → +0.00

**ตารางที่ 4.1 ฟีเจอร์ทั้ง 23 ตัวที่ใช้ในโมเดลปัจจุบัน (เรียงตามลำดับ index ซึ่งเป็นสัญญาระหว่าง Hub กับ ML Verifier — กำหนดใน `ml-service/app/features.py`)**

| กลุ่ม | จำนวน | ฟีเจอร์ |
|---|---|---|
| Temporal | 3 | `hour_of_day`, `day_of_week`, `hours_from_typical_login_time` |
| Geographic | 3 | `is_thailand`, `is_new_country`, `country_change_count_30d` |
| Device | 2 | `is_new_device`, `is_new_user_agent_family` |
| Velocity | 2 | `log_minutes_since_last_login`, `login_count_24h` |
| Brute-force | 1 | `failed_logins_24h` |
| Passkey / Device Trust | 4 | `passkey_count`, `passkey_age_days`, `new_passkey_recently_added`, `passkey_last_used_days` |
| Session | 2 | `concurrent_session_count`, `active_subsystem_count` |
| Behavioral | 1 | `weekday_usage_score` |
| OAuth | 1 | `scope_sensitivity_score` |
| Privilege | 2 | `ever_changed_permission`, `permission_change_age` |
| History | 1 | `confirmed_incident_count` |
| GeoVelocity | 1 | `impossible_travel_score` |

> **หมายเหตุ:** `is_weekend` และ `has_passkey` ถูกตัดออกจาก feature set เนื่องจาก collinear 100% กับ feature อื่น (`is_weekend = f(day_of_week)`, `has_passkey = f(passkey_count > 0)`) และถูกแทนด้วย `weekday_usage_score` (personalized) และ `passkey_count` ตามลำดับ การประเมินโมเดลในหัวข้อ 4.5 ใช้ชุดข้อมูลรุ่นก่อนหน้า (17 ฟีเจอร์) เนื่องจากไฟล์ `sessions.csv` บนระบบยังไม่ได้ถูก regenerate ด้วย 23-feature script การฝึกโมเดลใหม่ด้วยข้อมูล 23-feature เป็นงานที่อยู่ใน roadmap ต่อไป

ML Verifier ถูกออกแบบให้ **fail-safe ต่อความล้มเหลว** — ถ้าเรียก ML service ไม่สำเร็จไม่ว่ากรณีใด Hub จะรับค่า default `anomaly_score = 0.0, decision = pass` แล้วบันทึก log คำเตือนไว้ (กฎ B21) เพื่อไม่ให้ระบบล่มทั้งระบบเพียงเพราะบริการ ML ล่ม

### 4.3.4 Layer 4 — Risk Aggregator

ชั้นสุดท้ายรวมคะแนนจาก 3 ชั้นก่อนหน้าเข้าด้วยกัน (cap ไว้ที่ 1.00) แล้วตัดสินใจตามช่วงคะแนน ดังตารางที่ 4.2

**ตารางที่ 4.2 เกณฑ์การตัดสินใจของ Risk Aggregator (จาก `hub/backend/app/security/risk_aggregator.py`)**

| Risk Score | Decision (Enforce Mode) | Decision (Shadow Mode) |
|---|---|---|
| < 0.50 | allow | allow |
| 0.50 - 0.69 | warn | would_warn |
| 0.70 - 0.84 | challenge (Risk-Triggered MFA) | would_challenge |
| ≥ 0.85 | block | would_block |

ค่า threshold เหล่านี้ผ่านกระบวนการ calibration จากข้อมูลจริง (`scripts/calibrate_thresholds.py`) โดยพบว่าหากใช้ค่า challenge=0.50 (ค่าเริ่มต้นที่เคยออกแบบไว้) จะทำให้ False Positive Rate สูงถึง 24% บนชุดข้อมูลจริง เนื่องจาก normal user ที่มีอุปกรณ์ใหม่หรือ login นอกเวลาปกติเล็กน้อยได้คะแนนรวม 0.50-0.60 อยู่แล้ว การปรับ threshold challenge เป็น 0.70 ทำให้ FPR ลดลงเหลือ 5.8% ซึ่งเหมาะสมกว่าสำหรับระบบ MFA ที่มีผู้ใช้จริง

ทุก session จะถูกบันทึก `anomaly_score` และ `decision` ไว้ในตาราง `login_sessions` เสมอ ไม่ว่าจะอยู่ใน Shadow Mode หรือ Enforce Mode — ความแตกต่างคือใน Shadow Mode (`ML_SHADOW_MODE=true`) ระบบจะ "บันทึกว่าจะทำอะไร" (would_warn/would_challenge/would_block) แต่ยังปล่อยให้ผู้ใช้เข้าระบบได้ตามปกติ ทำให้สามารถ calibrate threshold ก่อนเปิดใช้งานจริง ซึ่งในโครงการนี้นำไปสู่การปรับ threshold challenge จาก 0.50 → 0.70 เพื่อลด False Positive Rate จาก 24% → 5.8%

## 4.4 ชุดข้อมูลสำหรับการพัฒนาโมเดล Machine Learning

### 4.4.1 การสร้างชุดข้อมูล

เนื่องจากระบบเป็นระบบใหม่ที่ยังไม่มีข้อมูลการล็อกอินจริงสะสมมากพอจะฝึกโมเดลได้ จึงสร้าง **ชุดข้อมูลสังเคราะห์ (synthetic dataset)** ด้วยสคริปต์ `ml-service/scripts/generate_data.py` โดยกำหนด `random.seed(42)` เพื่อให้ผลลัพธ์ทำซ้ำได้ ชุดข้อมูลประกอบด้วย session การล็อกอินทั้งหมด **10,500 รายการ** แบ่งเป็น

- **Normal sessions 10,000 รายการ** — สุ่มค่าฟีเจอร์ทั้ง 17 ตัวให้อยู่ในช่วงที่สอดคล้องกับพฤติกรรมผู้ใช้ทั่วไป เช่น ล็อกอินในเวลากลางวัน, จากประเทศไทย, ใช้อุปกรณ์ที่เคยใช้, ไม่มี failed login
- **Anomaly sessions 500 รายการ** — สร้างจาก 6 รูปแบบความผิดปกติ (anomaly patterns) ได้แก่ การล็อกอินกลางดึก (night), การล็อกอินจากต่างประเทศ (foreign), การล็อกอินถี่ผิดปกติในเวลาสั้น (burst), การใช้อุปกรณ์ใหม่ (new_device), การมี failed login พุ่งสูง (failed_spike), และการพยายาม takeover บัญชีที่มี Passkey อยู่แล้ว (passkey_takeover)

แต่ละ row ของชุดข้อมูลคือเวกเตอร์ฟีเจอร์ 17 ค่าตามตารางที่ 4.1 บวกกับ label คอลัมน์สุดท้าย (0 = normal, 1 = anomaly) ไฟล์ผลลัพธ์คือ `ml-service/data/sessions.csv` ขนาดประมาณ 728 KB

### 4.4.2 การแบ่งชุดข้อมูลสำหรับฝึกและทดสอบ

สคริปต์ `train_model.py` แบ่งข้อมูลด้วย `train_test_split` แบบ stratified ในสัดส่วน 80:20 (`TEST_SIZE = 0.20, RANDOM_STATE = 42`) ได้ชุด train 8,400 รายการ และชุด test 2,100 รายการ โดยยังคงสัดส่วน normal:anomaly เดิม (test set มี normal 2,000 รายการ และ anomaly 100 รายการ)

จุดสำคัญคือ Isolation Forest เป็นโมเดลแบบ **unsupervised** — ขั้นตอนการ fit โมเดลใช้เฉพาะ `X_train_normal` คือเฉพาะ session ที่เป็น normal ในชุด train จำนวน **8,000 รายการ** (8,400 รายการทั้งหมด หักด้วย anomaly ส่วน train 400 รายการ จาก stratified split 80% ของ anomaly 500 รายการ) โมเดลไม่เคยเห็นตัวอย่าง anomaly เลยระหว่างฝึก ส่วน label ของ anomaly ถูกใช้เพียงเพื่อ**ประเมินผล** หลังฝึกเสร็จแล้ว ซึ่งจำลองสถานการณ์จริงที่ระบบไม่มีตัวอย่างการโจมตีให้เรียนรู้ล่วงหน้า

> **ข้อสังเกต:** ชุดข้อมูล `sessions.csv` ที่ใช้ในการประเมิน (หัวข้อ 4.5–4.6) มี 17 ฟีเจอร์ ซึ่งเป็น version ก่อนการขยายเป็น 23 ฟีเจอร์ที่ implement แล้วในโค้ด (ตารางที่ 4.1) เนื่องจาก `generate_data.py` ยังไม่ได้รับการอัปเดตให้สร้างข้อมูล 23-feature ดังนั้นผลประเมินที่นำเสนอสะท้อนประสิทธิภาพของโมเดล 17-feature ซึ่งเป็น deployed version ปัจจุบัน — การ retrain ด้วย 23-feature data อยู่ใน roadmap สัปดาห์ถัดไป

## 4.5 ผลการประเมินประสิทธิภาพของโมเดล Isolation Forest

โมเดลที่ใช้คือ `IsolationForest(n_estimators=100, contamination=0.05, max_samples=256, random_state=42, n_jobs=-1)` ฝึกด้วย normal sessions ในชุด train จำนวน **8,000 รายการ** แล้วประเมินผลกับชุด test ที่ไม่เคยเห็นมาก่อน (2,100 รายการ) ผลลัพธ์จากการรันจริงแสดงในตารางที่ 4.3 และตารางที่ 4.4

**ตารางที่ 4.3 ผลการประเมินบนชุด Test (2,100 sessions)**

| Class | Precision | Recall | F1-score | Support |
|---|---|---|---|---|
| normal (0) | 1.00 | 0.94 | 0.97 | 2,000 |
| anomaly (1) | 0.47 | 1.00 | 0.64 | 100 |
| **Accuracy** | | | **0.95** | 2,100 |

**ตารางที่ 4.4 Confusion Matrix บนชุด Test**

| | Predicted Normal | Predicted Anomaly |
|---|---|---|
| **Actual Normal** | 1,888 | 112 |
| **Actual Anomaly** | 0 | 100 |

**AUC-ROC = 0.9946**

ผลลัพธ์แสดงให้เห็นว่าโมเดลตรวจจับ session ที่เป็น anomaly ได้ครบทั้งหมด (recall = 1.00 ไม่มี false negative เลยในชุด test) ซึ่งสำคัญมากสำหรับงาน security เพราะการ "พลาด" anomaly ไปเป็น normal คือความเสี่ยงที่ยอมรับไม่ได้ ในขณะที่ precision ของ class anomaly อยู่ที่ 0.47 หมายความว่าจาก session ที่โมเดลทักว่าผิดปกติ 212 รายการ มี 112 รายการที่จริง ๆ เป็น normal (false positive)

ในบริบทของระบบนี้ false positive ไม่ได้แปลว่าผู้ใช้ถูก block ทันที — คะแนนจาก Isolation Forest เป็นเพียง "หนึ่งใน 4 ชั้น" ของ Risk Aggregator (หัวข้อ 4.3.4) และ anomaly_score ที่สูงในชั้นที่ 3 เพียงอย่างเดียวมักจะดันคะแนนรวมไปอยู่ในช่วง 0.50-0.84 (challenge) คือขอ Passkey re-authentication เพิ่มเติม ไม่ใช่ block ตรง ๆ (ซึ่งต้องคะแนนรวม ≥ 0.85) ดังนั้น recall สูงพร้อม precision ปานกลางจึงเป็น trade-off ที่ยอมรับได้ในการออกแบบนี้ — เลือกที่จะ "ถามซ้ำ" บ่อยขึ้นเล็กน้อย แทนที่จะ "พลาด" การโจมตีไปเลย

จากค่า Youden's J statistic บน ROC curve ของชุด test พบว่าจุดตัดที่ให้ TPR (recall) = 0.99 มาพร้อมกับ FPR ≈ 0.045 ซึ่งสอดคล้องกับค่า `contamination = 0.05` ที่กำหนดไว้ตอนฝึกโมเดล ยืนยันว่าพารามิเตอร์ที่เลือกใช้เหมาะสมกับลักษณะข้อมูล

## 4.6 ผลการวิเคราะห์ด้วย SHAP

เพื่ออธิบายว่าฟีเจอร์ใดมีผลต่อคะแนน anomaly มากที่สุด ได้ใช้ **SHAP TreeExplainer** (Lundberg & Lee, 2017) วิเคราะห์โมเดล `iforest_v1.pkl` กับกลุ่มตัวอย่าง 500 sessions ที่สุ่มมาจากชุดข้อมูลทั้งหมด ผลลัพธ์ค่า mean(|SHAP value|) ของแต่ละฟีเจอร์ — ซึ่งบอกว่าฟีเจอร์นั้นมีอิทธิพลต่อผลการตัดสินของโมเดล "โดยเฉลี่ย" มากเพียงใด — แสดงในตารางที่ 4.5

**ตารางที่ 4.5 ค่าเฉลี่ย |SHAP value| ของแต่ละฟีเจอร์ (เรียงจากมากไปน้อย)**

| อันดับ | Feature | mean \|SHAP\| |

### การวิเคราะห์

ผลลัพธ์จริงจากการรัน SHAP แสดงให้เห็นว่ากลุ่มฟีเจอร์ที่มีอิทธิพลสูงสุดต่อโมเดลคือกลุ่ม **Temporal** (`is_weekend`, `hours_from_typical_login_time`, `day_of_week`, `hour_of_day`) และกลุ่ม **Velocity/Brute-force** (`failed_logins_24h`, `login_count_24h`) ซึ่งสอดคล้องกับ 3 ใน 6 รูปแบบ anomaly ที่ใช้สร้างชุดข้อมูล (night, burst, failed_spike) ที่ล้วนแสดงออกผ่านความผิดปกติด้านเวลาและความถี่ของการล็อกอินเป็นหลัก ฟีเจอร์กลุ่ม **Passkey/Device Trust** (`passkey_count`, `has_passkey`, `passkey_age_days`, `passkey_last_used_days`) ก็มีอิทธิพลอยู่ในระดับกลาง ซึ่งสอดคล้องกับรูปแบบ `passkey_takeover` และ `new_device`

สิ่งที่น่าสังเกตคือฟีเจอร์กลุ่ม **Geographic** สองตัว คือ `is_thailand` และ `is_new_country` มีค่า mean |SHAP| เท่ากับ 0 ในการวิเคราะห์รอบนี้ ซึ่งต่างจากที่คาดไว้ตอนออกแบบ (คาดว่าการเปลี่ยนประเทศควรเป็นสัญญาณความเสี่ยงที่สำคัญ) เมื่อตรวจสอบ `generate_data.py` พบว่าค่าทั้งสองนี้ผันแปรตามรูปแบบ `foreign` เพียงรูปแบบเดียวจาก 6 รูปแบบ และอาจมีความสัมพันธ์ (correlation) สูงกับฟีเจอร์ `country_change_count_30d` ทำให้ Isolation Forest "เลือก" ใช้ฟีเจอร์หลังในการแยกจุดข้อมูลแทน เนื่องจากแบ่งได้คมชัดกว่าในมุม tree-splitting — นี่เป็นข้อสังเกตที่นำไปสู่แนวทางปรับปรุงในอนาคต คือเพิ่มสัดส่วนตัวอย่าง `foreign` ในชุดข้อมูล หรือปรับวิธีสุ่มค่าฟีเจอร์ภูมิศาสตร์ให้มีความเป็นอิสระจากฟีเจอร์อื่นมากขึ้น เพื่อให้ SHAP สะท้อนความสำคัญของมิติภูมิศาสตร์ได้ชัดเจนกว่านี้ในรุ่นถัดไป

โดยรวมแล้ว ค่า SHAP ช่วยให้ทีมพัฒนาตรวจสอบได้ว่าโมเดลตัดสินใจจาก "เหตุผล" ที่สมเหตุสมผลในเชิงความปลอดภัย (เวลา, ความถี่, อุปกรณ์) ไม่ใช่จาก noise หรือ artifact ของการสร้างข้อมูล และผลลัพธ์เดียวกันนี้ยังถูกนำไปแสดงในหน้า ML Threshold Preview ของ Hub Admin Frontend เพื่อให้แอดมินเห็นเหตุผลประกอบทุกครั้งที่มี session ถูกตั้งค่าเป็น challenge หรือ block

### 4.7.2 Security Testing

การทดสอบความปลอดภัยอ้างอิงตาม OWASP Top 10 (2021) ครอบคลุมทั้ง 10 หมวด (`docs/security-review.md`) สรุปได้ว่า

- **Injection (SQL/XSS)** — ใช้ SQLAlchemy ORM (parameterized query) และ Jinja2 auto-escape ทุกหน้า ไม่พบช่องโหว่ SQL Injection หรือ XSS ในการทดสอบ
- **Broken Access Control** — ทุก endpoint ที่ละเอียดอ่อนมี dependency (`require_hub_admin`, `require_developer`, JWT `aud` check) ตามกฎ B1/B4/B19
- **Cryptographic Failures** — ใช้ RS256 (asymmetric) สำหรับ JWT, Argon2id สำหรับ secret/backup code, Fernet (AES) สำหรับ secret retrieval, HMAC-SHA256 สำหรับ one-time token, และ `hmac.compare_digest` สำหรับการเทียบค่าทุกจุดที่เกี่ยวกับ secret (กัน timing attack ตามกฎ B3)
- **CSRF** — วิเคราะห์แล้วพบว่าไม่จำเป็นต้องใช้ CSRF token แบบดั้งเดิม เพราะ Admin Console ใช้ Bearer JWT (ไม่ใช่ cookie-based session สำหรับ mutation) และทุก OAuth flow มี PKCE + state token ใน Redis ซึ่งเป็นมาตรการป้องกัน CSRF ที่ OWASP Cheat Sheet ยอมรับ
- **Vulnerable Components** — รัน `pip-audit` พบช่องโหว่เริ่มต้น 28 รายการ หลังอัปเดต/ปรับ dependency เหลือ 5 รายการ (ลดลง 82%) ที่เหลือเป็น transitive dependency ความเสี่ยงต่ำ (เช่น `ecdsa` ที่ไม่ถูกใช้งานจริงเพราะระบบใช้ RS256 ไม่ใช่ ECDSA)
- **Security Misconfiguration** — `ENABLE_DOCS=false` และ `config.validate_production()` ทำงานแบบ fail-fast คือปฏิเสธการ start service ถ้า production environment ยังใช้ค่า default ของ `SECRET_KEY`/`SECRET_ENCRYPTION_KEY`

ได้รันการสแกนเพิ่มเติมด้วย **OWASP ZAP Baseline Scan** กับ Hub backend พบรายการ "Missing Anti-CSRF Token" ระดับ Medium ซึ่งเป็น false positive ตามการวิเคราะห์ข้างต้น ส่วนรายการระดับ Low สองรายการ (X-Content-Type-Options และ Content-Security-Policy ไม่ถูกตั้งค่าในบางเส้นทาง) ได้แก้ไขแล้วด้วย `SecurityHeadersMiddleware` ที่ตั้งค่า header เหล่านี้ให้ทุก response แบบ global

### 4.7.3 Passkey Security Testing

ชุดทดสอบ `test_passkey_security.py` (12 test cases) มุ่งทดสอบภัยที่เฉพาะเจาะจงกับ WebAuthn ได้แก่

- **Replay Attack** — ทดสอบส่ง assertion เดิมซ้ำสองครั้ง ระบบต้องตรวจจับและปฏิเสธครั้งที่สองได้ (อาศัยการตรวจ `sign count` ที่ต้องเพิ่มขึ้นเสมอ)
- **Credential Substitution** — ทดสอบว่าไม่สามารถใช้ credential ของผู้ใช้ A ในการยืนยันตัวตนแทนผู้ใช้ B ได้
- **Enumeration** — ทดสอบ endpoint `login/start` ว่าค่า `allowCredentials` ที่ตอบกลับต้อง**ไม่ว่างเสมอ** ไม่ว่า email ที่ส่งมาจะมีอยู่ในระบบหรือมี Passkey จริงหรือไม่ (กฎ B43) — ถ้า email ไม่มี Passkey จริง ระบบจะสร้าง decoy credential descriptor ที่ deterministic ต่อ email นั้น (ด้วย `HMAC(SECRET_KEY, email)`) เพื่อไม่ให้ shape ของ response (ว่างหรือไม่ว่าง) รั่วข้อมูลว่า email นี้มี Passkey หรือไม่

ผลการทดสอบทั้งหมดผ่าน ซึ่งหมายความว่ามาตรการป้องกันทั้ง 3 รูปแบบทำงานได้ตามที่ออกแบบไว้

## 4.8 ผลการทดสอบ Risk-Triggered MFA (Step-Up Authentication)

ฟีเจอร์ Risk-Triggered MFA ถูกทดสอบทั้งแบบ unit test (22 รายการใน `test_risk_passkey_flow.py`) และแบบ scenario ตามระดับคะแนนความเสี่ยงที่ Risk Aggregator คำนวณได้ ซึ่งสอดคล้องกับเกณฑ์ 4 ระดับในตารางที่ 4.2 ดังตัวอย่างในตารางที่ 4.6

**ตารางที่ 4.6 ตัวอย่างผลลัพธ์ตาม Risk Score (Thresholds จาก `risk_aggregator.py`)**

| Risk Score | ระดับ | ผลลัพธ์ |
|---|---|---|
| 0.20 | < 0.50 | **Allow** — เข้าระบบได้ตามปกติ |
| 0.58 | 0.50 - 0.69 | **Warn** — เข้าระบบได้ แต่บันทึก log ไว้เพื่อเฝ้าระวัง |
| 0.75 | 0.70 - 0.84 | **Challenge** — เข้าสู่ flow Risk-Triggered MFA (Passkey Re-Auth / Grace / Force Enroll) |
| 0.91 | ≥ 0.85 | **Block** — ปฏิเสธการเข้าระบบทันที (single source of truth ที่ finalizer ตามกฎ B44) |

สำหรับกรณี Challenge (เช่น score = 0.75 ซึ่งอยู่ในช่วง 0.70–0.84) ระบบจะแยกเป็น 3 เส้นทางตามสถานะของผู้ใช้ ดังแผนภาพด้านล่าง

```text
Risk Aggregator: total score = 0.70 - 0.84 (Challenge)
        │
        ├── ผู้ใช้มี Passkey?  ─── YES ──► Passkey Re-Authentication
        │                                    (risk_challenge token, Redis TTL 5min,
        │                                     atomic getdel กัน replay — B47)
        │                                    ▼  ยืนยันผ่าน
        │                                    ออก authorization_code ต่อ OAuth flow
        │
        └── NO (ยังไม่มี Passkey)
              │
              ├── บัญชีอายุ < 7 วัน?  ─── YES ──► Allow Once + Banner
              │   (Grace Period                      (คำนวณ runtime จาก created_at — B48)
              │    runtime check)                    แสดง banner เตือนให้ลงทะเบียน Passkey
              │
              └── NO (พ้น Grace Period)  ──► Force Enrollment
                                              Email OTP gate (ยืนยันเจ้าของอีเมล — B45)
                                              ▼  OTP ผ่าน
                                              ลงทะเบียน Passkey ใหม่ + ออก backup code
                                              ▼  สำเร็จ
                                              ออก authorization_code ต่อ OAuth flow

หมายเหตุ: หากเบราว์เซอร์ไม่รองรับ WebAuthn → ทุกเส้นทางโอนไปยัง Account Recovery (B46)
```

1. **ผู้ใช้ที่มี Passkey อยู่แล้ว** — ระบบสร้าง one-time `risk_challenge` token (เก็บใน Redis, TTL 5 นาที, consume แบบ atomic getdel กัน replay ตามกฎ B47) แล้ว redirect ไปหน้า Passkey Re-Authentication ผู้ใช้ต้องยืนยันตัวตนผ่าน Passkey อีกครั้งก่อนจะดำเนินการ OAuth flow ต่อ
2. **ผู้ใช้ที่ยังไม่มี Passkey แต่บัญชีอายุน้อยกว่า 7 วัน (grace period)** — ระบบคำนวณ grace period แบบ runtime จาก `created_at` เสมอ (ไม่เก็บเป็น flag ค้างในฐานข้อมูล ตามกฎ B48) แล้วปล่อยให้เข้าระบบได้ครั้งนี้พร้อมแสดง banner เตือนให้ไปลงทะเบียน Passkey
3. **ผู้ใช้ที่ยังไม่มี Passkey และพ้น grace period แล้ว** — ระบบบังคับเข้าสู่ Force Enrollment flow คือต้องยืนยัน Email OTP ก่อน (ป้องกันผู้โจมตีที่ยึด session ไปบังคับเพิ่ม Passkey ของตัวเองได้ ตามกฎ B45) จากนั้นจึงให้ลงทะเบียน Passkey ใหม่พร้อมออก backup code

กรณีที่เบราว์เซอร์หรืออุปกรณ์ของผู้ใช้ไม่รองรับ WebAuthn เลย ทั้ง 3 เส้นทางข้างต้นจะ fallback ไปที่หน้า Account Recovery แทน (ตามที่อธิบายในหัวข้อ 4.2.5)

ผลการทดสอบทั้ง 22 test case ใน `test_risk_passkey_flow.py` ผ่านทั้งหมดภายในเวลารวม 6.23 วินาที และเมื่อรวมกับชุดทดสอบเดิม การ regression test ทั้งหมด 189 รายการผ่านทั้งหมดเช่นกัน (รายละเอียดอยู่ใน `tests/reports/risk_passkey_flow_2026-06-14.md`)

## 4.9 การอภิปรายผล

จากผลการพัฒนาและการทดสอบทั้งหมด สามารถอภิปรายได้ดังนี้

1. **ระบบทำหน้าที่เป็นศูนย์กลางการยืนยันตัวตนได้สำเร็จตามที่ออกแบบ** — ระบบย่อยทั้งสอง (หอพักและห้องสมุด) สามารถพึ่งพา Hub สำหรับ authentication และ authorization ได้ครบทั้ง OAuth 2.0 + PKCE, JWT verification ผ่าน JWKS, และการตรวจสอบสิทธิ์ผ่าน `access_list` โดยไม่ต้องพัฒนา Login UI หรือเก็บรหัสผ่านของผู้ใช้เอง

2. **Passkey ช่วยลดพื้นที่การโจมตีที่อิงรหัสผ่านได้จริง** ทั้งในแง่การล็อกอินหลักและในแง่การยืนยันตัวตนซ้ำสำหรับ Risk-Triggered MFA — ผลทดสอบ Passkey Security ทั้ง 12 รายการ (replay, substitution, enumeration) ผ่านทั้งหมด ยืนยันว่าการออกแบบรักษาคุณสมบัติ phishing-resistant ของ WebAuthn ไว้ได้ครบ

3. **การออกแบบ Risk Aggregator แบบ 4 ระดับ (allow/warn/challenge/block) และกระบวนการ calibration threshold ด้วย Shadow Mode** ให้ความละเอียดในการตอบสนองที่เหมาะสมกับพฤติกรรมผู้ใช้จริง — threshold challenge ที่ 0.70 (calibrated จากข้อมูลจริง) ลด FPR จาก 24% เหลือ 5.8% เมื่อเทียบกับค่าเริ่มต้น 0.50 การแยกระดับ `warn` (0.50–0.69) ออกมาช่วยให้ session ที่มีสัญญาณเสี่ยงอ่อน เช่น การใช้อุปกรณ์ใหม่เพียงอย่างเดียว ถูกบันทึกไว้เฝ้าระวังโดยไม่รบกวนประสบการณ์ผู้ใช้

4. **Isolation Forest ให้ผล recall = 1.00 บนชุดทดสอบ ซึ่งเหมาะกับบทบาท "หนึ่งในสี่ชั้น" ของ Hybrid RBA มากกว่าการเป็นผู้ตัดสินเพียงผู้เดียว** — precision 0.47 ของ class anomaly หมายความว่าถ้าใช้โมเดลนี้ตัดสิน block ตรง ๆ เพียงอย่างเดียว ผู้ใช้ปกติจำนวนหนึ่งจะถูกบล็อกผิด แต่ในการออกแบบนี้ ผลจาก ML เป็นเพียงคะแนนสะสมร่วมกับอีก 3 ชั้น ทำให้ false positive ของ ML เพียงอย่างเดียวมักจบลงที่การขอ "ยืนยันตัวตนซ้ำผ่าน Passkey" (challenge) ซึ่งใช้เวลาไม่กี่วินาที แทนที่จะ block ผู้ใช้จริงออกจากระบบ

5. **SHAP เผยให้เห็นทั้งสิ่งที่โมเดลเรียนรู้ได้ดีและข้อจำกัดของชุดข้อมูล** — ฟีเจอร์ด้านเวลาและความถี่ (Temporal/Velocity/Brute-force) มีอิทธิพลสูงสุดและสอดคล้องกับ anomaly pattern ส่วนใหญ่ที่ออกแบบไว้ ในขณะที่ฟีเจอร์ภูมิศาสตร์ (`is_thailand`, `is_new_country`) มีอิทธิพลใกล้ศูนย์ในรอบการวิเคราะห์นี้ — ข้อค้นพบนี้เป็นประโยชน์ในการปรับปรุงสคริปต์สร้างข้อมูลสังเคราะห์ในเวอร์ชันถัดไป เพื่อให้ตัวแทนของความเสี่ยงด้านภูมิศาสตร์ถูกเรียนรู้อย่างชัดเจนขึ้น

6. **ชุดทดสอบ 189 รายการที่ผ่านทั้งหมดครอบคลุมทั้ง happy path และ security edge case** แต่ยังมีรายการที่รอการทดสอบแบบ manual บนเบราว์เซอร์จริง (เช่น Windows Hello) และการแสดงผล banner grace period บน Hub Admin Frontend ซึ่งเป็นงานที่ยังเหลืออยู่ตาม roadmap สัปดาห์ถัดไป

## 4.10 สรุปบทที่ 4

ผลการพัฒนาแสดงให้เห็นว่า Central Auth Hub สามารถทำหน้าที่เป็นระบบศูนย์กลางสำหรับการยืนยันตัวตนและจัดการสิทธิ์ของระบบย่อยในมหาวิทยาลัยได้ตามขอบเขตที่ตั้งไว้ ทั้งในส่วนของ OAuth 2.0 + PKCE, OIDC ผ่าน Google OAuth, Passkey/WebAuthn แบบครบวงจร และ Hybrid Risk-Based Authentication แบบ 4 ชั้น

ในส่วนของโมเดล Machine Learning ผลการทดลองกับชุดข้อมูลสังเคราะห์ 10,500 รายการ พบว่า Isolation Forest ให้ค่า AUC-ROC = 0.9946 และ recall = 1.00 สำหรับ class anomaly บนชุดทดสอบ ซึ่งเหมาะสมกับบทบาทของโมเดลในระบบ คือเป็นหนึ่งในสี่ชั้นของการประเมินความเสี่ยง ไม่ใช่ผู้ตัดสินใจเพียงผู้เดียว ผลการวิเคราะห์ด้วย SHAP ยืนยันว่าโมเดลให้น้ำหนักกับฟีเจอร์ด้านเวลา ความถี่ และอุปกรณ์เป็นหลัก ซึ่งสมเหตุสมผลกับนิยามของ anomaly ที่ใช้สร้างชุดข้อมูล

ในด้านการทดสอบ ระบบผ่านการทดสอบอัตโนมัติ 189 รายการ และผ่านการตรวจสอบความปลอดภัยตาม OWASP Top 10 รวมถึงการสแกนด้วย OWASP ZAP โดยไม่พบช่องโหว่ระดับ Critical สุดท้าย ฟีเจอร์ Risk-Triggered MFA ที่ wire เสร็จในสัปดาห์ที่ 9-10 ทำให้ระบบสามารถตอบสนองต่อความเสี่ยงที่ตรวจพบได้แบบ graded response ตั้งแต่ allow, warn, challenge ด้วย Passkey re-authentication หรือ force enrollment ไปจนถึง block ครบตามวัตถุประสงค์ของโครงการ
