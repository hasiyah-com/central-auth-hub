# แนวทางการพัฒนาต่อยอดเพื่อแก้ไขข้อจำกัดของระบบประเมินความเสี่ยง (ฉบับปรับปรุง)

> **หมายเหตุการปรับปรุง:** ฉบับเดิมระบุบางหัวข้อ (Threat Intelligence, Attack Scenario
> Generation, Feedback Loop) ไว้ในส่วน "แนวทางในอนาคต" ทั้งที่ระบบได้ดำเนินการไปแล้ว
> ฉบับนี้จึงแยกเป็น **(ก) ข้อจำกัดที่ได้แก้ไขแล้วในงานนี้** ออกจาก **(ข) แนวทางในอนาคตที่แท้จริง**
> เพื่อความถูกต้องและสะท้อนผลงานตามจริง

---

## 1. หลักการ

ระบบที่พัฒนาขึ้นสามารถประเมินความเสี่ยงจากการเข้าสู่ระบบได้อย่างมีประสิทธิภาพ โดยใช้
Hybrid Risk-Based Authentication ร่วมกับแบบจำลอง Isolation Forest และหลังการปรับปรุง
กระบวนการประเมิน (ดูหัวข้อที่ 2) สามารถลดอัตราการแจ้งเตือนผิดพลาด (False Positive Rate)
บนทราฟฟิกจริงจากร้อยละ 47.1 เหลือร้อยละ 6.4 ซึ่งต่ำกว่าเกณฑ์เป้าหมายร้อยละ 10

อย่างไรก็ตาม ระบบยังคงมีข้อจำกัดที่พบได้ทั่วไปในงานวิจัยด้าน Risk-Based Authentication (RBA)
และ Anomaly Detection ได้แก่

1. **การตรวจจับผู้โจมตีที่เลียนแบบพฤติกรรมของผู้ใช้งานจริง (Targeted Attacker)** —
   จากการประเมินด้วยการจำลองผู้โจมตี 4 ระดับ พบว่าระบบตรวจจับผู้โจมตีระดับ naive และ VPN
   ได้ร้อยละ 100 แต่ตรวจจับผู้โจมตีแบบ targeted ที่ทราบทั้งประเทศ อุปกรณ์ และช่วงเวลาที่
   เหยื่อใช้งาน ได้เพียงร้อยละ 8.7–30 ซึ่งเป็นข้อจำกัดเชิงทฤษฎีของ RBA ทุกระบบที่อาศัย
   ความผิดปกติของบริบทเป็นสัญญาณ

2. **การขาดข้อมูลการโจมตีจริงที่มีป้ายกำกับ (Labeled Real Attack Dataset)** —
   ระบบยังไม่มีเหตุการณ์การยึดบัญชี (Account Takeover) ที่เกิดขึ้นจริงและได้รับการยืนยัน
   ทำให้การวัดค่า Recall ต้องอาศัยการจำลองการโจมตี ซึ่งเป็นข้อจำกัดร่วมของงานวิจัย RBA
   โดยทั่วไป (มีเพียงบริการขนาดใหญ่ที่มีทีมความมั่นคงปลอดภัยจึงจะมีข้อมูลดังกล่าว)

> ทั้งนี้ ข้อจำกัดที่ 1 (Targeted Attacker) ได้รับการชดเชยบางส่วนแล้วด้วยการรองรับ Passkey
> (WebAuthn/FIDO2) ในระบบ ซึ่งผู้โจมตีไม่สามารถปลอมแปลงได้แม้จะทราบรหัสผ่าน — กล่าวคือ
> RBA และ Passkey รับมือภัยคุกคามคนละลักษณะและเสริมกัน (ดูหัวข้อที่ 4)

## 2. ข้อจำกัดที่ได้ดำเนินการแก้ไขแล้วในงานนี้

หัวข้อนี้อธิบายมาตรการที่ **ได้ผนวกเข้ากับระบบแล้ว** ซึ่งบางส่วนเป็นแนวทางที่งานวิจัยด้าน
RBA แนะนำให้พัฒนาต่อยอด

### 2.1 การสร้างข้อมูลผิดปกติจากสถานการณ์การโจมตี (Attack Scenario Generation)

แทนการสร้างข้อมูลผิดปกติแบบสุ่ม ระบบสร้างชุดข้อมูลการโจมตีโดยอ้างอิงจากงานวิจัย RBA
(Wiefling et al., 2023) ผ่านการจำลองผู้โจมตี **4 ระดับตามระดับความรู้เกี่ยวกับเหยื่อ**
ได้แก่ very_naive, naive, vpn และ targeted โดยแต่ละระดับสร้างจากเซสชันจริงของผู้ใช้แล้ว
แปลงเฉพาะคุณลักษณะที่สะท้อนการโจมตี (labeled by construction) ครอบคลุมสถานการณ์:
การเข้าสู่ระบบจากอุปกรณ์ใหม่ ประเทศใหม่ เวลาที่ผิดปกติ Impossible Travel การเข้าสู่ระบบ
พร้อมกันหลายอุปกรณ์ และการเปลี่ยน User-Agent

> **สถานะ:** ดำเนินการแล้ว — `build_attack_set.py`, `generate_grounded_data.py`
> **ผลลัพธ์:** วัด Recall แยกตามระดับผู้โจมตีได้ (naive 100%, VPN 96.7%, targeted 30%)

### 2.2 การใช้ข้อมูลชื่อเสียงของ IP (IP Reputation / Threat Intelligence)

ระบบผนวกข้อมูล Threat Intelligence จาก **ipsum threat feed** (รวบรวม IP ที่ถูกรายงานว่า
เป็นภัยคุกคาม) โดยดาวน์โหลดและปรับปรุงข้อมูลอัตโนมัติทุก 24 ชั่วโมง และตรวจสอบทุกครั้งที่
มีการเข้าสู่ระบบ (`is_blacklisted`) ผลลัพธ์ถูกใช้เป็นคุณลักษณะร่วม (`is_attack_ip` →
`confirmed_incident_count`) ในการคำนวณความเสี่ยง

> **สถานะ:** ดำเนินการแล้ว — `ip_blacklist.py`, `ipsum_refresh.py` (scheduler)
> **ขยายต่อได้:** ดูหัวข้อ 3.2 (external API แบบ real-time)

### 2.3 ระบบ Feedback สำหรับปรับปรุงแบบจำลอง

ระบบมีกลไกให้ผู้ดูแลระบบระบุผลการประเมินว่าเป็น False Positive, True Positive หรือ
Normal ผ่าน API (`POST /admin/ml/sessions/{id}/feedback`) โดยจัดเก็บใน `MLFeedback`
และนำไปใช้เป็นป้ายกำกับ (label) สำหรับการฝึกแบบจำลองรอบถัดไป (`export_labeled_data.py`)

> **สถานะ:** ดำเนินการแล้ว (แบบ manual) — ผู้ดูแลระบบให้ป้ายกำกับ แล้ว re-export/retrain
> **ขยายต่อได้:** ดูหัวข้อ 3.3 (auto-retrain pipeline)

### 2.4 การปรับปรุงกระบวนการประเมิน (Evaluation Methodology)

นอกเหนือจากคุณลักษณะและแบบจำลอง งานวิจัยนี้ได้ปรับปรุงความรัดกุมของการประเมิน ได้แก่
การแก้ปัญหา Data Leakage ในการสกัดคุณลักษณะแบบ point-in-time การแบ่งชุดฝึก/ทดสอบแบบ
held-out และการแยกทราฟฟิกทดสอบออกจากการวัดผล ซึ่งทำให้ค่า FPR ลดลงจากร้อยละ 47.1
เหลือร้อยละ 6.4 โดยไม่ปรับค่าขีดแบ่งหรือกฎใด

> **สถานะ:** ดำเนินการแล้ว — เป็นส่วนหนึ่งของ contribution เชิง methodology ของงาน

## 3. แนวทางการพัฒนาต่อยอด (Future Work)

หัวข้อนี้เป็นแนวทางที่ **ยังไม่ได้ดำเนินการ** และเสนอไว้สำหรับการพัฒนาในอนาคต โดยจัดลำดับ
ตามความสอดคล้องกับข้อจำกัดในหัวข้อที่ 1

### 3.1 การขยายชุดข้อมูลการโจมตี → ผู้โจมตีระดับสูงสุด + การทดสอบเจาะจริง
**(แก้ข้อจำกัดที่ 2 โดยตรง)**

ปัจจุบันการจำลองครอบคลุมผู้โจมตี 4 ระดับ แต่ยังขาดระดับที่ 5 (very_targeted) ซึ่งต้องอาศัย
ค่าจริงจากเหตุการณ์ยึดบัญชี งานในอนาคตควร (ก) เพิ่มการทดสอบเจาะระบบด้วยผู้วิจัยเอง
(red-team) เพื่อสร้างข้อมูลการโจมตีจริงจำนวนหนึ่งไว้ตรวจสอบความสมจริงของการจำลอง และ
(ข) รวบรวมเหตุการณ์จริงเมื่อระบบเปิดใช้งานเป็นระยะเวลานาน

### 3.2 การเพิ่มข้อมูล Threat Intelligence แบบ Real-time
**(เสริมข้อจำกัดที่ 1)**

ต่อยอดจาก ipsum feed (หัวข้อ 2.2) โดยเพิ่มการเรียก API ภายนอกแบบ real-time เช่น
**AbuseIPDB, AlienVault OTX, VirusTotal** เพื่อตรวจสอบชื่อเสียงของ IP ที่ยังไม่อยู่ใน
รายการ ก่อนนำผลไปใช้เป็นปัจจัยร่วม แนวทางนี้ช่วยตรวจจับผู้โจมตีที่ใช้ IP ซึ่งเคยเกี่ยวข้อง
กับการโจมตีแต่ยังไม่ถูกบันทึกในฐานข้อมูลภายใน

### 3.3 การพัฒนา Pipeline การฝึกแบบจำลองอัตโนมัติ (Automated Retraining)

ต่อยอดจาก feedback loop แบบ manual (หัวข้อ 2.3) โดยพัฒนาให้ระบบฝึกแบบจำลองใหม่โดย
อัตโนมัติเมื่อป้ายกำกับจากผู้ดูแลระบบสะสมถึงเกณฑ์ที่กำหนด พร้อมการตรวจสอบคุณภาพก่อนนำ
แบบจำลองใหม่ไปใช้ (guardrail) เพื่อให้ระบบเรียนรู้จากข้อมูลจริงได้อย่างต่อเนื่องโดยไม่ต้อง
อาศัยการดำเนินการด้วยมือ

### 3.4 การเพิ่มการตรวจสอบความน่าเชื่อถือของอุปกรณ์ (Device Attestation)
**(แก้ข้อจำกัดที่ 1 โดยตรง)**

แม้ระบบจะรองรับ Passkey ที่ผูกกับฮาร์ดแวร์อยู่แล้ว แต่การประเมินความเสี่ยงยังใช้ User-Agent
ซึ่งปลอมแปลงได้ งานในอนาคตสามารถเพิ่มการยืนยันความน่าเชื่อถือของอุปกรณ์ผ่าน
**Android Play Integrity API, Apple DeviceCheck หรือ TPM บน Windows** เพื่อลดโอกาสที่
ผู้โจมตีแบบ targeted จะปลอมแปลงอุปกรณ์ให้เหมือนเหยื่อ

### 3.5 การประเมินความเสี่ยงระหว่างการใช้งาน (Continuous Authentication)
**(แก้ข้อจำกัดที่ 1 โดยตรง)**

ระบบปัจจุบันประเมินความเสี่ยงเฉพาะช่วงเข้าสู่ระบบ (Login) งานในอนาคตสามารถประเมินความ
เสี่ยงอย่างต่อเนื่องระหว่างการใช้งานจากพฤติกรรมการเรียกใช้ API รูปแบบการเข้าถึงข้อมูล และ
ความถี่การใช้งาน หากพบความเปลี่ยนแปลงอย่างมีนัยสำคัญ ระบบสามารถร้องขอการยืนยันตัวตน
เพิ่มเติมหรือยุติเซสชันได้ทันที แนวทางนี้ช่วยตรวจจับผู้โจมตีแบบ targeted ที่ผ่านการยืนยัน
ตอน login ไปได้ (เนื่องจากการตรวจจับหลัง login อาศัยพฤติกรรมการใช้งานซึ่งเลียนแบบได้ยากกว่า)

> **หมายเหตุสถาปัตยกรรม:** ระบบนี้ไม่ใช่ SSO — Hub มองไม่เห็นกิจกรรมภายในระบบย่อยโดยตรง
> การทำ Continuous Authentication จึงต้องออกแบบกลไกส่งสัญญาณพฤติกรรมจากระบบย่อยกลับมายัง
> Hub เพิ่มเติม ซึ่งเป็นความท้าทายเชิงสถาปัตยกรรมที่ต้องพิจารณา

### 3.6 การพัฒนาแบบจำลองให้รองรับการเรียนรู้แบบต่อเนื่อง (Online / Incremental Learning)

Isolation Forest ที่ใช้ต้องฝึกใหม่ทั้งหมดเมื่อมีข้อมูลเพิ่ม (แม้ในทางปฏิบัติจะใช้เวลาน้อยที่
ปริมาณข้อมูลปัจจุบัน) งานในอนาคตสามารถศึกษาเทคนิค Online Learning หรือ Incremental
Anomaly Detection เพื่อรองรับการปรับตัวต่อพฤติกรรมผู้ใช้ที่เปลี่ยนแปลงเมื่อระบบขยายขนาด

## 4. การเชื่อมโยงแนวทางกับข้อจำกัด

| ข้อจำกัด | แนวทางที่รับมือ |
|---|---|
| **Targeted Attacker** (ข้อจำกัดที่ 1) | ✅ Passkey (มีแล้ว) · 3.4 Device Attestation · 3.5 Continuous Auth · 3.2 Threat Intel |
| **ขาด Real Attack Data** (ข้อจำกัดที่ 2) | 3.1 red-team + very_targeted · 3.3 auto-retrain (สะสม label จริง) |

> ข้อสังเกตสำคัญ: RBA ที่ประเมิน ณ ช่วง login เพียงอย่างเดียวมีเพดานในการตรวจจับผู้โจมตี
> แบบ targeted การรับมือที่มีประสิทธิภาพจึงต้องอาศัยกลไกที่ **ไม่พึ่งความผิดปกติของบริบท**
> (Passkey — ผูกฮาร์ดแวร์) หรือ **ตรวจสอบต่อเนื่องหลัง login** (Continuous Auth) ควบคู่กัน

---

## 5. สรุป

งานวิจัยนี้ได้ดำเนินการแก้ไขข้อจำกัดสำคัญบางส่วนไปแล้ว ได้แก่ การสร้างข้อมูลการโจมตีจาก
สถานการณ์ที่อ้างอิงงานวิจัย การใช้ข้อมูล IP Reputation การมีกลไก Feedback สำหรับปรับปรุง
แบบจำลอง และการปรับปรุงความรัดกุมของกระบวนการประเมินจนลด FPR เหลือร้อยละ 6.4

สำหรับข้อจำกัดที่ยังคงอยู่ — โดยเฉพาะการตรวจจับผู้โจมตีแบบ targeted และการขาดข้อมูลการโจมตี
จริง — งานในอนาคตที่เสนอประกอบด้วยการขยายชุดข้อมูลการโจมตีและการทดสอบเจาะจริง การเพิ่ม
Threat Intelligence แบบ real-time การพัฒนา pipeline การฝึกอัตโนมัติ การเพิ่ม Device
Attestation การประเมินความเสี่ยงแบบต่อเนื่อง และการศึกษาแบบจำลองที่เรียนรู้ต่อเนื่อง

แนวทางดังกล่าวเชื่อมโยงกลับไปยังข้อจำกัดที่ระบุไว้อย่างชัดเจน และเมื่อพิจารณาร่วมกับกลไก
Passkey ที่ระบบมีอยู่ จะช่วยเสริมความสามารถของระบบบริหารจัดการตัวตนและสิทธิ์แบบรวมศูนย์
ให้รองรับภัยคุกคามที่ซับซ้อนมากขึ้นได้ในอนาคต
