## 1. เหตุผลที่ต้องมีรุ่นใหม่

`build_profiles_v2.spread_over_days()` ใช้ `weekend_rate` เป็น **น้ำหนักต่อวัน**
แทนที่จะเป็น **สัดส่วนของ login ที่เกิดวันหยุด** ตามที่ pre-registration ของ P48
ประกาศไว้ (B71 · `tests/reports/generator_weekend_rate_bug_2026-09-09.md`)

ผลคือสัดส่วนที่ generate ได้จริงต่ำกว่าที่ประกาศ 0.27–0.37 เท่า และมีเพดานที่
**0.2667** แม้ตั้งค่าสูงสุด — ประชากร P48 จึงไม่เคยมีผู้ใช้ที่ทำงานวันหยุดเป็นหลัก
ทั้งที่ประกาศว่ามี 25% ของประชากร

การแก้ generator เปลี่ยนพฤติกรรมของ **ทุกโปรไฟล์** → เป็นคนละประชากร
ต้องรันรอบใหม่ทั้งชุดและ **ห้ามนำตัวเลขมารวมกับ P48 รุ่นเดิม**

## 3. สิ่งที่แก้ใน generator

```
w_weekend = (p x n_weekday) / ((1 - p) x n_weekend)      # วันธรรมดามีน้ำหนัก 1.0
```

| กรณีขอบเขต | พฤติกรรม |
|---|---|
| `p = 0` | ไม่สร้าง login วันหยุดเลย |
| `0 < p < 1` | ใช้สูตรแปลงน้ำหนัก |
| `p = 1` | สร้างเฉพาะวันหยุด |
| ไม่มีวันหยุด หรือไม่มีวันธรรมดาในช่วง | `ValueError` พร้อมข้อความชัดเจน |
| `p` นอก `[0, 1]` | `ValueError` |

**ไม่มีการแก้อื่นใดใน generator นอกจากจุดนี้**

### 3.1 tolerance ของ `weekend_rate`

```
| observed - target | <= max(0.02, sampling_CI)
```

| เป้าหมาย | ช่วงที่ยอมรับ |
|---|---|
| 0.05 | 0.03 – 0.07 |
| 0.15 | 0.13 – 0.17 |
| 0.30 | 0.28 – 0.32 |
| 0.40 | 0.38 – 0.42 |

บังคับด้วย `tests/test_generator_weekend_rate.py`

## 4. เกณฑ์และงบที่ **ไม่เปลี่ยน** จากรอบก่อน

| ระดับ | งบ FPR |
|---|---|
| warn | ≤ 5.0% |
| challenge | ≤ 1.0% |
| block | ≤ 0.2% |

**วิธีตัดสิน** — cluster-aware CI สามทาง (`passed` / `failed` / `inconclusive`)
โดย `inconclusive` = ไม่ deploy (fail-closed) · ต้องผ่าน **ทุกขนาดข้อมูล**

**เกณฑ์รายงาน** — mean / median / p90 ของ per-user FPR · cluster CI ·
จำนวนผู้ใช้ที่เกินงบเป็น outlier report แยก · recall@challenge แยก attack family ·
แยกทุกขนาดประวัติ · `max user FPR` ไม่ใช้เป็น gate

**scoring / threshold ไม่ถูกแตะในรอบนี้** — ยืนยันด้วย `tests/test_scoring_freeze.py`
ผ่าน 10/10 ไฟล์ ก่อนเริ่มรอบ

---

## 5. Gate ที่ต้องผ่านตามลำดับ

| # | Gate | เกณฑ์ |
|---|---|---|
| 1 | Population integrity | 48 คน · alias / seed / split ไม่ชนกับ P48 เดิม |
| 2 | Distribution fidelity | ทุกโปรไฟล์อยู่ใน tolerance ของ `weekend_rate` |
| 3 | Leakage | train / validation / holdout ไม่ซ้ำกัน |
| 4 | Shortcut | ไม่พบฟีเจอร์เดี่ยวที่แยก attack ได้ตามเกณฑ์ (AUC > 0.99 หรือ coverage < 0.05) |
| 5 | Scoring integrity | scoring freeze ผ่าน |
| 6 | Challenge FPR | cluster-aware CI แยกทุกขนาดประวัติ |
| 7 | Warn / Block FPR | ตรวจแบบเดียวกัน |
| 8 | Recall | รายงานรวมและแยก attack family |
| 9 | Holdout | ยังปิดอยู่ ถ้า validation `inconclusive` หรือ `failed` |

## 6. กติกาที่ล็อกไว้ก่อนเห็นผล

1. **ห้ามแก้ threshold, scoring หรือ roster หลังเห็นผล**
2. ถ้า audit (gate 3–4) ไม่ผ่าน → **ยกเลิกรอบนี้** และสร้าง version/seed ใหม่
   ไม่ใช่แก้แล้วรันซ้ำบนชุดเดิม
3. โปรไฟล์ holdout 16 คน **ห้ามเปิด** จนกว่า validation จะได้ `passed`
4. ผลของ P48-T2 รายงานแยกจาก P48 รุ่นเดิมเสมอ
5. P48 รุ่นเดิมและ tag `p48-validation-inconclusive` ยังคงอยู่ ไม่เขียนทับ
