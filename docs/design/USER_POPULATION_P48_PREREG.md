`build_profiles_v2.SPEC` มีโปรไฟล์ **12 คนที่ตายตัว** และทุก seed ใช้ชุดเดิม —

ผลที่วัดได้: ผู้ใช้คนเดียว (U01) ครองสัดส่วน challenge FPR **61.8%** ในบาง seed
และค่า FPR ระดับประชากรถูกกำหนดโดย "U01 ระเบิดหรือไม่" มากกว่าคุณสมบัติของระบบ

→ ข้อสรุปบทที่ 4 ต้องมีหน่วยทดลองมากพอที่ค่าเฉลี่ยระดับประชากรจะมีความหมาย

## 2b. seed ของข้อมูล (เติม 8 ก.ย. 2569 — ก่อนวัดผลใด ๆ)

เอกสารฉบับแรกประกาศเฉพาะ**ประชากรโปรไฟล์** แต่ลืมประกาศ **seed ของการสุ่มข้อมูล**
ซึ่งเป็นคนละแกนกัน (โปรไฟล์ = ใคร · seed = การสุ่มเหตุการณ์ของคนนั้น)
เติมไว้ที่นี่ก่อนมีการวัดใด ๆ และบันทึกว่าเป็นการเติมภายหลัง

    SEEDS_P48 = [301, 302, 303, 304, 305]

ใช้ชุดเดียวกันทั้งสอง stratum — สิ่งที่ถูก "กัน" ไว้คือ **ตัวโปรไฟล์** ไม่ใช่ seed

| ขั้น | โปรไฟล์ | split ภายในผู้ใช้ |
|---|---|---|
| 6–7 validation | P48-validation (32) | `tune` เท่านั้น |
| 8 holdout | P48-holdout (16) | `test` เท่านั้น · เปิดครั้งเดียว |

seed `[101-115]` ถูกใช้ไปแล้วในรอบก่อน และ `[201-205]` ถูกจองไว้ให้ Round 3
(conditional L3) จึงเริ่มชุดใหม่ที่ 301 · การเปิด holdout ต้องผ่าน holdout ledger
ตามกฎ B68 เช่นเดิม

## 2c. Amendment #2 — ตรึง `incidents = 0` (8 ก.ย. 2569 · ก่อนเปิด holdout)

**สิ่งที่พบ:** `rule_engine.SCORE_RULES_SPEC` มีกฎ
`confirmed_incident_count >= 1 -> challenge` เป็น **policy floor** ผู้ใช้ที่มีค่านี้
จึงถูก challenge **ทุก login ตลอดกาล** โดยผลลัพธ์ไม่ขึ้นกับโมเดลเลย

การสุ่ม `incidents` ที่ประกาศไว้เดิม (8%) จึงเป็นความผิดพลาดเชิงสเปค — มันไม่ใช่
คุณลักษณะพฤติกรรม แต่เป็น **สถานะเชิงนโยบายที่กำหนดผลลัพธ์แบบตายตัว**

**หลักฐาน** (validation seed 301 · size 50 · Config B · 32 โปรไฟล์):

| user | FPR | สัดส่วนจาก policy floor | `incidents` |
|---|---|---|---|
| P03 | 100.0% | 100% | 1 |
| P44 | 100.0% | 100% | 1 |
| P29 | 100.0% | 100% | 1 |
| ที่เหลือ | ≤ 5.4% | — | 0 |

3 คนใน 32 ดัน mean ขึ้น 9.4 pp ด้วยตัวเอง → ตัวเลขที่ได้วัด "สัดส่วนผู้ใช้ที่เคยมี
incident" ไม่ใช่อัตราแจ้งเตือนผิดของโมเดล · L12 ที่มาจากการวัดของจริงมี
`incidents = 0` ทั้ง 12 คน ปัญหานี้จึงไม่เคยโผล่ในรอบก่อน

**การแก้:** ตรึง `incidents = 0` ทั้งประชากร · ผู้ใช้ที่ติด policy floor ถาวรอยู่
**นอกขอบเขต** ของงบ FPR เพราะผลลัพธ์ของเขาไม่มีข้อมูลเกี่ยวกับโมเดล

**ความซื่อตรงของการแก้:**
- holdout **ยังไม่ถูกเปิด** — การแก้ไม่กระทบความบริสุทธิ์ของ holdout
- ตัวเลข validation ที่วัดก่อนหน้านี้ถือเป็น pre-amendment และถูกแทนที่ทั้งหมด
- เป็นการแก้ **ข้อผิดพลาดเชิงสเปค** ที่พิสูจน์ได้โดยไม่ต้องดูตัวเลขประสิทธิภาพ
  (กฎ policy floor กำหนดผลลัพธ์ตายตัวอยู่แล้วตั้งแต่อ่านโค้ด) ไม่ใช่การปรับตามผล
- generator ยังเรียก `rng.choices` ตามเดิมแล้วทิ้งค่า เพื่อไม่ให้ลำดับการสุ่มขยับ →
  ประชากรเปลี่ยน **เฉพาะฟิลด์นี้ฟิลด์เดียว** พิสูจน์ด้วย hash ใน
  `test_amendment_2_changed_only_the_incidents_field`
- ต้องรัน shortcut/leakage audit (ขั้นที่ 5) ใหม่ เพราะ generator เปลี่ยน

## 4. เกณฑ์ที่ต้องรายงาน (ขั้นที่ 7)

ทุกค่าต้องแยกตาม history size **50 / 100 / 500 / 1000 / 5000**:

1. **mean user FPR** ระดับประชากร
2. **median** และ **p90** ของ per-user FPR
3. **hierarchical / cluster CI** ของ mean
4. **จำนวนผู้ใช้ที่เกินงบ** (พร้อมรายชื่อ + ค่าของแต่ละคน เป็น outlier report แยก)
5. **Recall@challenge แยก attack family**
6. การกระจายของ per-user FPR (อย่างน้อย min / q25 / median / q75 / p90 / max)

**`maximum user FPR ≤ 1%` ห้ามใช้เป็น gate หลัก** — เมื่อจำนวนผู้ใช้เพิ่มขึ้น
ค่าสูงสุดจะสูงขึ้นเองตามธรรมชาติ (order statistic) ทำให้เกณฑ์เข้มขึ้นโดยไม่ได้ตั้งใจ
เมื่อขยายประชากร → ใช้ **mean + CI** และ **p90** เป็นเกณฑ์ และรายงาน outlier แยก

## 5. ลำดับที่ต้องทำตาม (ห้ามข้าม)

1. commit เอกสารนี้ **ก่อน** เขียน generator
2. สร้าง generator + roster (ขั้นที่ 4)
3. ตรวจ shortcut / leakage ของ generator (ขั้นที่ 5) — ถ้าพบ ต้องแก้ก่อนวัดใด ๆ
4. รัน Config B + baseline บน **P48-validation** เท่านั้น (ขั้นที่ 6)
5. รายงานตามเกณฑ์ §4 ด้วย cluster-aware CI (ขั้นที่ 7)
6. เปิด **P48-holdout** ครั้งเดียว เฉพาะเมื่อ validation ผ่าน (ขั้นที่ 8)
7. **ถ้าไม่ผ่าน หยุดที่ Shadow — ห้ามปรับ threshold ต่อ** (ขั้นที่ 9)
