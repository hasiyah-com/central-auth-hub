# ออกแบบ: subsystem novelty เป็น evidence family เดียว

ร่าง 6 ก.ย. 2569 · ขั้นที่ 3 ของแผนแก้ cold-start FPR
อ้างอิงหลักฐาน: [cold_start_fpr_rootcause_2026-09-06.md](../../hub/backend/tests/reports/cold_start_fpr_rootcause_2026-09-06.md)

## 1. ปัญหาที่ต้องแก้

`evaluate_behavior()` ปัจจุบันมีสามสัญญาณที่ยิงจาก **เหตุการณ์เดียวกัน**
("ผู้ใช้เข้าระบบ X ที่ไม่ตรงกับรูปแบบเดิมของตน") แต่ถูกนับเป็นสามหลักฐานอิสระ:

| สัญญาณ | น้ำหนัก | เงื่อนไข |
|---|---|---|
| `new_subsystem` | +0.30 | `subsystem_id not in seen_subsystems` |
| `subsystem_rarity` | +0.15 | เคยใช้แต่ rarity ≥ 0.95 (ตัดกับข้างบน) |
| `scope_escalation` | +0.25 | `scope − p90(ของคนนี้) ≥ 0.20` |

`new_subsystem` และ `scope_escalation` **ไม่เป็นอิสระต่อกัน**: ระบบที่ผู้ใช้ไม่เคยเข้า
มักเป็นระบบที่ scope ต่างจากเดิม · วัดได้จริงที่ U01 — 78 จาก 81 เหตุการณ์ที่ถูก
challenge มีทั้งคู่ยิงพร้อมกัน รวมเป็น `0.30 + 0.25 = 0.55`

ผลคือ **นับหลักฐานซ้ำ** และเกิดมวลก้อนใหญ่ที่ค่าเดียว (0.55 = 9.8% ของเหตุการณ์
ปกติของ U01) ซึ่ง ECDF map ไปที่ 0.9955 — เหนือเกณฑ์ challenge 0.995 แค่ 0.0005

## 2. หลักการออกแบบ

> เหตุการณ์เดียว = หลักฐานชิ้นเดียว · ความรุนแรงมาจากสมาชิกที่แรงที่สุดในตระกูล
> ไม่ใช่ผลรวมของสมาชิก

และเพิ่มหลักการที่สอง ซึ่งเป็นต้นเหตุจริงของ cold start:

> "ไม่เคยเห็น" จากประวัติ 50 ครั้ง เป็นหลักฐานที่อ่อนกว่า "ไม่เคยเห็น" จาก 5,000 ครั้ง
> — น้ำหนักของ novelty ต้องขึ้นกับ**ปริมาณประวัติที่รองรับข้ออ้างนั้น**

## 3. โครงสร้างที่เสนอ

```
novelty_evidence = C_novelty(eff_n) × novelty_strength
scope_evidence   = C_scope(eff_n)   × escalation_strength

family_score = FAMILY_WEIGHT × max(novelty_evidence, scope_evidence)
```

**คูณ confidence แยกกันก่อน `max`** (ไม่ใช่ `C × max(N, S)`) เพราะฐานความมั่นใจ
ของสองสัญญาณต่างกัน — ถ้าใช้ confidence ตัวเดียว ระบบที่**เคยเห็นแล้ว**แต่ scope
เพิ่มขึ้นจริง จะถูกทำให้เป็นศูนย์เพียงเพราะ novelty ยังไม่มั่นใจ ซึ่งผิด

| สมาชิก | `strength` |
|---|---|
| ไม่เคยใช้ระบบนี้ | `1.00` |
| เคยใช้แต่นานๆ ที | `rarity` (0.95–1.0 → 0.95–1.0) |
| scope เกิน p90 ของตนเอง | `min(1, (scope − p90) / SCOPE_FULL_MARGIN)` |

`FAMILY_WEIGHT` เริ่มที่ **0.30** (เท่ากับสมาชิกที่แรงที่สุดเดิม — ไม่ทำให้
สัญญาณอ่อนลงเมื่อประวัติยาว แต่ตัดการนับซ้ำออก)

### `eff_n` — ขนาดตัวอย่างที่ใช้อ้างได้จริง

ใช้ **จำนวนวันที่มีการใช้งาน** (`profile["active_days"]`) ไม่ใช่จำนวนแถว —
login 50 ครั้งรวดเดียวในวันเดียวไม่ได้บอกเรื่องกิจวัตรเท่ากับ login 50 วัน
(temporal clustering) · โปรไฟล์เก่าที่ไม่มีฟิลด์นี้ตกกลับไปใช้จำนวนแถว

### `C_novelty` — rule-of-three confidence **heuristic**

ถ้าสังเกต n ครั้งแล้วไม่พบระบบ X เลย ขอบบน 95% ของความถี่จริงของ X คือ ≈ `3/n`
ข้ออ้าง "X ใหม่จริงสำหรับคนนี้" จะน่าเชื่อก็ต่อเมื่อขอบบนนั้น **ต่ำกว่า** โหมด
ที่เล็กที่สุดที่เรายังถือว่าเป็นพฤติกรรมประจำ:

```
C_novelty(eff_n) = clamp(1 − (3/eff_n) / ROUTINE_MODE_FLOOR, 0, 1)
C_novelty(eff_n ≤ 0) = 0
```

**เรียกว่า heuristic ไม่ใช่ probability** — สูตร rule of three สมมติว่าเหตุการณ์
ค่อนข้างเป็นอิสระ ขณะที่ login จริงมี temporal clustering · การใช้ `eff_n` เป็นวัน
บรรเทาปัญหาแต่ไม่ได้ทำให้สมมติฐานเป็นจริง จึงห้ามรายงานค่านี้เป็นความน่าจะเป็น

### `C_scope` — ทางลาดตามจำนวนตัวอย่าง (คนละสูตรโดยตั้งใจ)

scope escalation ไม่ใช่ข้ออ้างว่า "ไม่เคยพบ" (rule of three ใช้ไม่ได้) แต่เป็น
การประมาณ **ควอนไทล์ p90** ซึ่งต้องการจำนวนตัวอย่างพอประมาณจึงจะเสถียร:

```
C_scope(eff_n) = clamp((eff_n − SCOPE_MIN_OBS) / (SCOPE_FULL_OBS − SCOPE_MIN_OBS), 0, 1)
C_scope(eff_n ≤ 0) = 0
```

`ROUTINE_MODE_FLOOR` = ความถี่ต่ำสุดที่ถือว่า "เป็นกิจวัตรของผู้ใช้คนนี้"
ค่าเริ่มต้นที่เสนอ **0.05** (5%) — ต่ำกว่าโหมด SUB_A ของ U01 ที่ 10%

| n | 3/n | confidence | family_score เมื่อ strength=1 |
|---|---|---|---|
| 50 | 0.060 | **0.00** | 0.00 |
| 100 | 0.030 | 0.40 | 0.12 |
| 300 | 0.010 | 0.80 | 0.24 |
| 500 | 0.006 | 0.88 | 0.26 |
| 5000 | 0.0006 | 0.99 | 0.30 |

**ผลที่คาดต่อเคส U01:** ที่ size 50 มวล 0.55 หายไปทั้งก้อน (49 เหตุการณ์)
ที่ size 5000 ยังได้ ~0.30 (จาก 0.55 เดิม — ตัดการนับซ้ำ)

**ผลข้างเคียงที่ตั้งใจ:** `confidence(n)` และ `rarity` เป็นค่าต่อเนื่อง →
คะแนน L2 ไม่เป็นแลตทิซหยาบอีก → การเลือก threshold ไม่กระโดดทีละก้อน

## 4. `min_action = "challenge"` ที่ไม่เคยทำงาน (ต้องตัดสินใจ)

โค้ดปัจจุบันตั้ง `min_action = "challenge"` พร้อมคอมเมนต์ว่า "policy floor"
แต่ `risk_fusion.fuse()` **ทิ้งค่านี้** — มีเพียง `policy.min_action` จาก
`SCORE_RULES_SPEC` ที่ `kind == "policy_floor"` เท่านั้นที่มีผล

วัดยืนยันแล้ว: ใน 81 เหตุการณ์ที่ U01 ถูก challenge ได้
`policy min_action distribution: {None: 81}` — floor ไม่เคยถูกใช้เลยสักครั้ง

**เสนอให้ตัดออกพร้อมคอมเมนต์อธิบาย** ไม่ใช่ต่อสาย เพราะการทำให้มันทำงานจริงจะ
บังคับ challenge ทุกครั้งที่เข้าระบบใหม่ ซึ่งแย่กว่าเดิมมาก (U01 = 10.6% ของ login)
→ บันทึกเป็นบั๊ก B70: โค้ดที่ประกาศว่าเป็น policy floor แต่ไม่มีผล และไม่มีเทสจับ

**ตรวจก่อนลบ (ทำแล้ว 6 ก.ย. 2569):**

| ตรวจ | ผล |
|---|---|
| consumer ของ `behavior.min_action` | `risk_aggregator.aggregate()` เท่านั้น — **ไม่มี caller ใน production** (`risk_engine` ใช้ `fuse`) · legacy harness 2 ไฟล์ · ทุกที่ใช้ `getattr(..., None)` จึงลบได้ปลอดภัย |
| เปิดเผยใน API / schema / frontend | **ไม่พบ** — ไม่ต้องมี contract/migration test |
| `PolicyOutcome.min_action` (ของจริง) | ยังอยู่ครบ · มีเทสยืนยันว่าไม่ถูกลบตามไป |
| เทสใหม่ที่บังคับ evidence-only | `tests/test_l2_evidence_only.py` |

**ข้อสังเกตที่ต้องบันทึกแยก:** เทสเดิมหลายไฟล์ (`test_behavior_rarity`,
`test_rule_engine_v2_signals`, `test_tier2_catches_evasive`, `test_scope_conformance`)
วัดผลผ่าน `aggregate()` ซึ่ง **ไม่ใช่เส้นทางที่ production ใช้** — เป็นอาการเดียวกับ
B66 (วัดคนละคอนฟิกกับที่ deploy) · ยังไม่แก้ในรอบนี้ แต่ต้องบันทึกไว้

## 5. พารามิเตอร์ที่ต้องทดลอง (ขั้นที่ 4)

| พารามิเตอร์ | ค่าเริ่มต้น | กริดที่จะกวาดบน validation |
|---|---|---|
| `ROUTINE_MODE_FLOOR` | 0.05 | 0.02 · 0.05 · 0.10 · 0.20 |
| `FAMILY_WEIGHT` | 0.30 | 0.25 · 0.30 · 0.40 |
| `SCOPE_FULL_OBS` | 100 | 50 · 100 · 200 |
| `SCOPE_FULL_MARGIN` | 0.40 | 0.30 · 0.40 |

⚠️ **0.05 เป็นเพียงค่ากลางของกริด ไม่ใช่ default หรือ frozen value**
จนกว่าจะจบ validation · ห้ามอ้างในรายงานว่าเป็นค่าที่เลือกแล้ว

### เกณฑ์เลือกค่าจากกริด (ขั้นที่ 5)

ตามลำดับ:

1. ผ่าน **cluster-aware FPR** (ทุกขนาด · verdict ไม่ใช่ failed)
2. **recall@challenge** ลดไม่เกิน tolerance ที่ประกาศไว้ล่วงหน้า
3. recall ของ **`new_subsystem`** · **`scope_escalation`** และ **campaign** ต้องไม่ตก
   เกินเกณฑ์แยกรายตระกูล
4. ถ้าผลเท่ากัน เลือกสูตรที่ **เรียบง่ายและอนุรักษ์กว่า**
5. ต้องรายงานแยกตามขนาดประวัติ **50 / 100 / 500 / 1000 / 5000** เสมอ

> **ห้ามถือว่า "มวล 0.55 ของ U01 หายทั้งก้อน" เป็นความสำเร็จ** จนกว่าจะยืนยันว่า
> attack ที่เกี่ยวกับ subsystem/scope ไม่ได้หายตามไปด้วย — เป็นเงื่อนไขบังคับ
> ก่อนสรุปผลขั้นที่ 5
