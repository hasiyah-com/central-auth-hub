# ฟีเจอร์และเกณฑ์คะแนนของระบบประเมินความเสี่ยง

อ้างอิงโค้ด `feature_extraction.py`, `rule_engine.py`, `behavior_profiling.py`, `risk_aggregator.py`, `l3_fallback.py` และ `ml-service/app/features.py` ณ รุ่นที่เพิ่มตารางนี้ ฟีเจอร์ 23 ตัวเรียงตามเวกเตอร์ของ L3 point model; ทุกค่าดึงจากเวลาก่อนเหตุการณ์ที่กำลังประเมิน การเปลี่ยนโมเดลหรือกฎต้องตรวจตารางนี้ใหม่

**วิธีอ่าน:** คอลัมน์ L1/L2 แสดงคะแนนที่ *กฎ* เพิ่มเมื่อเข้าเงื่อนไข หนึ่งฟีเจอร์อาจถูกใช้ทั้งสองชั้นจึงมีคะแนนทั้งสองคอลัมน์ (เว้นกฎเครื่องใหม่ที่ L2 ตั้งใจไม่บวกซ้ำ) เครื่องหมาย `—` หมายถึงชั้นนั้นไม่มีเกณฑ์ให้คะแนนตรง ๆ; ค่าฟีเจอร์ยังส่งเข้า L3 ได้เสมอ L3 point เป็น Isolation Forest ที่ใช้ทั้ง 23 ค่า ไม่มีน้ำหนัก/เกณฑ์คะแนนคงที่แยกแต่ละฟีเจอร์ ค่า SHAP เมื่อคำนวณได้เป็นผลต่อโมเดลในเหตุการณ์นั้น ไม่ใช่คะแนนที่บวกกับ L1/L2 หรือสาเหตุที่พิสูจน์แล้ว ค่าช่วงรับข้อมูลใน `ml-service/app/features.py` เป็นเกณฑ์ตรวจรูปแบบ ไม่ใช่เกณฑ์เตือน

ข้อ 11 และ 21 มี **เกณฑ์ซ้อนกันจริงในโค้ดปัจจุบัน**: อย่าตีความแถวที่สองว่าเป็นเฉพาะช่วง 3–4 ครั้งหรือ 2–7 วัน ความล้มเหลวที่ผูกด้วยอีเมลมีข้อจำกัดเพิ่มเติมตามโค้ด เพื่อไม่ให้ผู้ที่รู้อีเมลอย่างเดียวบล็อกบัญชีคนอื่น

L2 มีสัญญาณที่ไม่ได้เป็นคอลัมน์แยกในเวกเตอร์ 23 ตัว: เข้าระบบย่อยใหม่เมื่อประวัติ ≥20 ได้ +0.30 และขั้นต่ำ challenge; ระบบย่อยที่เคยใช้น้อยมาก +0.15; ลายเซ็นอุปกรณ์ที่เคยเห็นแต่น้อยมาก +0.15 ถ้าประวัติ ≥20. ประวัติ L2 เป็นช่วง 30 วัน; ต่ำกว่า 5 เซสชันได้ cold-start +0.20. L1 ยังตรวจกฎจาก IP blacklist, IP หลายบัญชีเมื่อไม่อยู่หลัง shared NAT, ความเสี่ยงจากระบบย่อยอื่นใน 30 นาที และการเดินทางเป็นไปไม่ได้จากประเทศกับเวลา โดยบางกฎบล็อกทันทีและไม่เรียก L3

L4 รวมคะแนน L1+L2 และตัดไว้ไม่เกิน 1: <0.50 allow, ≥0.50 warn, ≥0.70 challenge; ≥0.85 แต่ไม่มีหลักฐาน hard block ยังคง challenge. ขั้นต่ำ challenge จากกฎมีผลแม้คะแนนไม่ถึง 0.70. L3 ไม่เพิ่มคะแนนในผลรวมนี้; ตัวสำรอง L3 ใช้คะแนน point รวม หรือ percentile ต่อประเภทผู้ใช้เมื่อมีไฟล์ calibration โดยพิจารณาเฉพาะเมื่อ L1+L2 allow. ตัวสำรอง legacy ที่เปิดผ่านแฟล็กอาจยก allow เป็น warn แต่ไม่เพิ่มคะแนน และ sequence view เป็นการเฝ้าระวังแยกต่างหาก

ในหน้า Session Detail ตารางฟีเจอร์ชั้น 3 แสดง **ค่าอินพุตทั้ง 23 ตัว** ของเหตุการณ์ใหม่โดยไม่ต้องคำนวณ SHAP บนเส้นทาง login; เซสชันเก่าที่ไม่เคยเก็บเวกเตอร์จะไม่มีตารางย้อนหลัง SHAP ถ้ามีจึงแสดงค่าผลต่อโมเดลของแต่ละตัว เฉพาะตัวที่มีจริง เครื่องหมาย — ไม่ได้หมายถึงศูนย์

## ชั้น 3 มุมมองลำดับเวลา (sequence)

L3 ยังมีโมเดลรายบุคคลอีกมุมมองหนึ่งซึ่ง **ไม่ใช่เวกเตอร์ point 23 ตัว**: เก็บค่าดิบ 6 ตัวต่อเหตุการณ์ แล้วเทียบแต่ละตัวกับ median/IQR ของประวัติผู้ใช้คนนั้น (`(ค่า−median)/max(IQR, 1e−6)`). หน้าต่าง 5 เหตุการณ์สร้างสถิติ 3 แบบต่อค่า: `mean` ค่าเฉลี่ย, `slope` ค่าสุดท้ายลบค่าแรก, และ `ptp` ค่าสูงสุดลบค่าต่ำสุด จึงได้ **18 มิติ** ตามตาราง (หนึ่งแถวแทนชื่อสามมิติ)

| ค่าดิบ | ชื่อไทย | แหล่ง/วิธีคำนวณ | มิติในหน้าต่าง 5 เหตุการณ์ |
|---|---|---|---|
| `gap_log` | เวลาห่างจากครั้งก่อน | ฟีเจอร์ point ข้อ 9 | `gap_log_mean_w5`, `gap_log_slope_w5`, `gap_log_ptp_w5` |
| `scope` | ความอ่อนไหวของสิทธิ์ | ฟีเจอร์ point ข้อ 19 | `scope_mean_w5`, `scope_slope_w5`, `scope_ptp_w5` |
| `passkey_age_log` | อายุ passkey แบบลอการิทึม | `log1p(max(passkey_age_days,0))` | `passkey_age_log_mean_w5`, `passkey_age_log_slope_w5`, `passkey_age_log_ptp_w5` |
| `weekday_usage` | วันที่ไม่คุ้นเคย | ฟีเจอร์ point ข้อ 18 | `weekday_usage_mean_w5`, `weekday_usage_slope_w5`, `weekday_usage_ptp_w5` |
| `hours_from_typical` | ชั่วโมงห่างจากเวลาประจำ | ฟีเจอร์ point ข้อ 3 | `hours_from_typical_mean_w5`, `hours_from_typical_slope_w5`, `hours_from_typical_ptp_w5` |
| `sub_rarity` | ความหายากของระบบย่อย | `1−(จำนวนครั้งในระบบย่อยนี้+1)/(จำนวนประวัติ+3)` | `sub_rarity_mean_w5`, `sub_rarity_slope_w5`, `sub_rarity_ptp_w5` |

โมเดล sequence ก็ไม่มีคะแนนกฎตายตัวรายมิติ ความพร้อมขึ้นกับจำนวนเหตุการณ์ก่อนหน้า: 100 ครั้งสำหรับวินิจฉัย, 1,000 สำหรับระดับ warn, 2,000 สำหรับระดับ challenge ตาม `ml-service/app/sequence.py`; ผล sequence ที่ระบบส่งมาเป็นข้อมูลเฝ้าระวังและคำอธิบายสูงสุด 5 มิติ ส่วนตารางที่เพิ่มใน Session Detail แสดงเวกเตอร์ **point 23 ตัว** ของเหตุการณ์ใหม่
